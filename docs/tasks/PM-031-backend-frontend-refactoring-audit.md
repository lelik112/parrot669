# PM-031 — Backend and Frontend Refactoring Audit

**Title:** аудит технического долга backend и frontend без запуска переписывания.

**Status:** planned. **Priority:** P2. **Owner:** Марк / Product Manager.

**Agent:** Марк. **Role:** Product Manager. **Scope:** постановка задачи, координация, документация; без кода и технических изменений.

**Audit executors (not claimed):**
- Игорь — backend audit.
- Денис — frontend audit.

Указание исполнителя не означает автоматический claim или начало работы. Исполнитель должен подтвердить старт по правилам команды.

**Recommended model:** Sol. **Recommended reasoning:** High.

**Reason:** нужен широкий анализ нескольких связанных слоёв после быстрого развития MVP: backend, frontend, auth, search, calendar, messaging и host flows. Цель — найти только изменения, влияющие на скорость развития, качество и риски, а не улучшать код ради эстетики.

## Goal

Определить, где накопленный технический долг реально мешает развитию PARROT 669 и какие изменения имеют смысл до дальнейшего масштабирования продукта.

## Context

В PARROT уже реализованы:

- auth;
- properties;
- search;
- calendar/iCal;
- verification;
- messaging;
- host cabinet;
- profiles.

Многие изменения делались итеративно для MVP. Требуется независимая оценка текущего состояния.

Аудит не является подготовкой к переписыванию проекта.

## Requirements

### Backend audit — Игорь

Проверить:

- структуру модулей;
- Routes/Main;
- service/repository boundaries;
- доменные границы;
- дублирование логики;
- тестируемость;
- сложность добавления новых фич;
- кандидатов на выделение отдельных модулей.

### Frontend audit — Денис

Проверить:

- структуру страниц;
- JS-модули;
- повторение логики;
- API/auth слой;
- состояние форм;
- i18n;
- переиспользование UI;
- готовность к следующим фичам:
  - profile;
  - public host profile;
  - FAQ;
  - новые trust signals.

## Result format

# REFACTOR AUDIT

## NOW

Что мешает прямо сейчас:

- проблема;
- влияние;
- оценка S/M/L;
- риск Low/Medium/High;
- рекомендация.

## NEXT

Что желательно сделать в ближайших этапах:

- проблема;
- влияние;
- оценка;
- риск;
- рекомендация.

## LATER

Что можно оставить без изменений:

- причина;
- оценка.

## DO NOT TOUCH

Что не нужно рефакторить и почему.

## Critical rules

Не предлагать рефакторинг только потому, что код выглядит некрасиво.

Каждая рекомендация должна быть связана хотя бы с одной причиной:

- мешает выпускать фичи;
- увеличивает риск багов;
- усложняет тестирование;
- создаёт дублирование бизнес-логики;
- создаёт риск при росте нагрузки/команды.

Не превращать аудит в переписывание проекта.

## Acceptance criteria

- [ ] Есть отдельный backend audit.
- [ ] Есть отдельный frontend audit.
- [ ] Все рекомендации имеют проблему, влияние, размер, риск и причину.
- [ ] Отдельно указано, что не нужно трогать.
- [ ] Нет предложений rewrite без доказанной проблемы.
- [ ] Результат позволяет Марку и Алексею принять решение о следующем этапе.

- Большой rewrite.
