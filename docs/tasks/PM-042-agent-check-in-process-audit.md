## Goal / Problem

Алексей сейчас вручную открывает чат каждого агента, чтобы сообщить о назначении. Марк уже ведёт очередь в репозитории, но запись в Markdown не будит агента и сама по себе не подтверждает claim. Требуется понять путь от назначения до автономного возобновления исполнителя без дублей и без ложного заявления «он уже работает».

### NEXT — минимальный процесс

1. Марк в единственной карточке пишет `Assigned to: имя / роль`, узкий scope, приоритет, ссылку на acceptance, дату и ожидаемый следующий шаг; обновляет индекс. `Owner` сам по себе не равен назначению.
2. Внешний check-in ищет **изменения назначения** для конкретного агента. Пожелание владельца — примерно каждые 5 минут (288 проверок в сутки на агента). Доступные здесь встроенные Automations имеют расписание не чаще одного раза в час; GitHub webhook поддерживает события pull request, но не изменение Markdown-карточки. Их нельзя выдавать за готовый пятиминутный wake-up. Для 5 минут нужно проверить отдельный внешний механизм, а модель запускать только при новом назначении.
3. При изменении оркестратор должен возобновить **нужного** агента с ID и актуальной версией карточки. Исполнитель перечитывает статус, чужие claims, блокеры и модель, затем записывает собственный подписанный claim с временем UTC. Если карточка изменилась одновременно, он перечитывает её и уступает уже принятому claim; Марк разрешает конфликт.
4. Допустимые состояния: `planned → assigned → claimed/in progress → in review → done`. `blocked` не запускает работу автоматически; после снятия блокера Марк делает явное переназначение. QA берёт только явно выделенный ей/ему scope; `in review` не перезапускает автора разработки.
5. После выполнения агент записывает evidence и следующий шаг в карточке, а Марк обновляет индекс/статус. При ошибке запуска назначение сохраняется, но claim отсутствует: задача видна как ожидающая, повторный запуск допустим только с дедупликацией.
6. Автоматизацию считать работающей только после сквозного подтверждения: назначение → запуск нужного агента без ручного открытия чата → один claim → результат в репозитории. Созданная карточка или календарный триггер этого не доказывают.
