# PM-001 — Проверка сохранённых контрольных дат

**Title:** Airbnb calendar control: выбрать даты в PARROT и проверить сохранённое задание.

**Status:** planned. **Priority:** P1. **Owner:** не заявлен.

**Area:** backend + frontend календарной проверки. **Source:** BUG-015.

**Product decision:** [D002 accepted](../decisions/D002-calendar-control-dates.md). **Updated:** 2026-09-24, Марк / PM.

## Goal

Пользователь понимает, какие ночи изменить, а успех относится к выполнению сохранённого задания по текущему источнику.

## Problem

v1 не принимает выбранный диапазон и засчитывает любое изменение будущей доступности. Посторонняя бронь может дать успех; после Check исчезает инструкция.

## Context

Владелец 24.09 подтвердил: выбрать даты у нас → сохранить → изменить в Airbnb → проверить. [QA и критерии BUG-015](../qa/2026-09-24/PARROT669-QA-HOST-2026-09-24.md) имеют приоритет над старым описанием v1 в [backend contract](https://github.com/lelik112/parrot669-backend/blob/main/docs/calendar-ownership-verification.md). Исправление ещё не объявлено выпущенным.

## User

Владелец, подключающий календарь; гость, читающий сигнал проверки.

## Value

Ясное действие для владельца и сигнал, основанный на выполнении конкретного задания.

## Solution

Сохранённое на сервере задание: даты, ожидаемое действие, исходное состояние и привязка к источнику. Техническую структуру выбирает разработчик. До реализации записать предлагаемые допустимые исходные состояния и выбор «закрыть/открыть»; при изменении продукта согласовать с PM.

## Requirements

- До внешнего действия выбрать ночи в PARROT и успешно сохранить задание. Не показывать «теперь измените Airbnb» до получения пригодного исходного состояния.
- Ожидаемое действие однозначно и выполнимо; неподходящий диапазон объясняется до расходования действия пользователя. Не предлагать изменять существующие брони.
- Проверять выбранный диапазон A и требуемое изменение. Изменение только B не влияет на успех A.
- При ожидании, reload и возврате показывать те же даты, действие, инструкцию, статус и следующий шаг. Не заменять сохранённые даты внутри попытки незаметно.
- Источник задания должен оставаться тем же. Старое задание не засчитывается новому источнику.
- Сохранить обычный flow подключения, проверки listing ID, синхронизации, импорта, enable/disable и удаления. Не менять семантику Reserved/Not available для поиска.
- Сохранить существующие правила попыток/ожидания, если отдельное изменение не принято: три неудачные попытки, cooldown 24 часа, исходный срок 30 минут и повторы Check по текущему контракту. Объяснять пользователю ошибки и ожидание.
- Сохранить языки EN/ES/CA/RU и включённую последнюю ночь формы владельца. После успеха объяснить возможность вернуть временное изменение.

## Acceptance criteria

- [ ] Без выбранных и сохранённых дат и исходного состояния переход к внешнему действию невозможен.
- [ ] Полное требуемое изменение A после исходного состояния даёт успех; изменение только B — не даёт.
- [ ] Нет изменения, исходно целевое состояние, частичное выполнение и ошибка загрузки не дают успех.
- [ ] Даты и инструкция восстанавливаются после перезагрузки и остаются во время повторов/преждевременного Check.
- [ ] Замена источника и повторные нажатия не позволяют применить чужое/устаревшее задание.
- [ ] Положительный и отрицательный цикл проверены на контролируемом календаре; регрессии существующего календарного flow проверены в согласованной среде.
- [ ] UI описывает проверенное изменение календаря, не личность или юридическое владение; опубликованный контракт соответствует результату.

## Alternatives

Любое изменение календаря; исправление только подсказок. Простой кандидат на первое задание — временное закрытие подходящих свободных ночей; это предложение для оценки, не скрытое утверждённое ограничение.

## Rejected

Зачёт чужого диапазона; подмена проверки задания изменением UID/метаданных; закрытие дефекта одной правкой текста.

## Success criteria

Контролируемые A/B-сценарии дают правильный результат, владелец проходит шаги без поиска инструкции в чате. На пилоте фиксируются завершение и причины неудачи; числовая цель пока не задана.

## Not doing

Airbnb API/OAuth/scraping, проверка личности/права собственности, переписывание интеграции, автоматическое изменение реальных броней, новый запрет поиска объектов без Airbnb. Публикация ссылки — отдельная PM-002.

## Dependencies

Перед claim проверить текущую работу агента календарей и пересечения рефакторинга. PM-002 использует итоговый смысл проверки, но не блокирует реализацию этого принятого требования. QA нужен контролируемый источник и разрешённый сценарий.
