## Поиск: подтверждено кодом, скорость не измерена

В [`SearchService.search` (строки 85–137)](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/search/SearchService.scala#L85-L137) основной `searchAvailable` вызывается один раз, после чего `matches.traverse` отдельно загружает для **каждого** объекта listings, cleaning fee и link source. Реализация каждого из трёх методов [`SearchRepository` (48–63)](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/search/SearchRepository.scala#L48-L63) завершает свой SQL отдельным `.transact(xa)`; [`PublicLinks.source`](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/domain/PublicLinks.scala#L21-L31) — один SQL с lateral join. `traverse` и обычный `mapN` для IO здесь последовательны. Вычисление времени внутри tuple не является запросом к БД.

| Выдано основным SQL | Обращений к БД (вывод из кода, не замер) |
| ---: | ---: |
| 0 | 1 |
| 1 | 4 |
| 10 | 31 |
| 50 | 151 |

Время и реальное число результатов неизвестны: среда этого аудита без `sbt`, `psql`, `docker` и доступного непроизводственного PostgreSQL с репрезентативными данными. Нет ни трассировки SQL/latency, ни замеров 1/10/50; таблица отражает число вызовов в одном успешном проходе без ошибок. Не давал нагрузку на production. Для замера нужны изолированный Postgres со схемой/правдоподобным объёмом объектов и периодов, запросы 1/10/50 результатов, число SQL/р50/р95 и `EXPLAIN (ANALYZE, BUFFERS)` основного SQL.

**Failure path:** `propertyCleaningFee` использует `.unique` для `properties`. Если объект удалён между успешным `searchAvailable` и этим запросом, row отсутствует и эффект падает; `traverse` прерывает **весь ответ**, включая другие объекты. Ошибка любого одного SQL enrichment также прерывает выдачу; `SearchRoutes` оборачивает только `Either[ServiceError]`, а не исключение из БД ([строки 25–55](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/search/SearchRoutes.scala#L25-L55)). Это детерминированный вывод из управления эффектами, не наблюдавшийся production incident. При отсутствии listing запрос вернёт `[]`, при отсутствии source — `None`; само по себе это **не** ломает поиск. Раздельные транзакции могут читать разные версии fee/listing/verification при одновременном редактировании. Цена вычисляется из ночной суммы основного SQL плюс текущий cleaning fee, а price range фильтруется после enrichment; `PublicLinks.published` фильтрует видимые валидные ссылки и вычисляет статус по текущему source ([строки 43–63](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/domain/PublicLinks.scala#L43-L63)). Текущие [SearchSuite (161–203)](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/test/scala/com/parrot669/search/SearchSuite.scala#L161-L203) проверяют обычную цену/ссылку/отсутствие ссылки, но не SQL-count или отказ одного enrichment.

**Рекомендация — NEXT / P2, размер S для диагностики и M для возможного исправления, риск Medium.** Сначала отдельной узкой задачей воспроизвести пропавшую строку/ошибку через repository stub и измерить 1/10/50 на изолированной БД. Если выдача замедляется за согласованный бюджет или ошибка воспроизводится, загрузить нужные fee/listing/source пакетно для всех `propertyId` и согласовать поведение при исчезнувшем объекте (пропускать его без потери остальных), сохранив точные `PriceEstimate`, `links` и сортировку. Ошибку самой БД не маскировать как пустую выдачу. Проверка регресса: отсутствие listing, скрытая/неверная ссылка, verified/pending/recheck, полный/неполный тариф, цена с fee, конкурентное удаление; сравнить количество SQL и latency до/после. Пока нет чисел, не утверждаю необходимость общего rewrite.
