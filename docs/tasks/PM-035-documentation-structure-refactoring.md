# PM-035 — Documentation Structure Refactoring

**Title:** уменьшить технический долг документации и ускорить восстановление контекста команды.

**Status:** in progress — Марк / Product Manager. **Priority:** P2. **Owner:** Марк / Product Manager.

**Agent:** Марк. **Role:** Product Manager. **Scope:** структура документации, процессы работы команды; без кода и изменений приложения.

**Recommended model:** Sol. **Recommended reasoning:** Medium.

**Reason:** текущая документация стала большим рабочим хранилищем истории. Нужно отделить текущее состояние от журналов изменений, чтобы восстановление контекста было быстрее и надёжнее.

## Goal

Сделать структуру docs удобной для ежедневной работы команды и восстановления сессии после потери контекста.

## Problem

Сейчас некоторые документы одновременно содержат:

- актуальное состояние;
- историю изменений;
- обсуждения;
- инструкции процесса.

Из-за этого:

- сложно быстро восстановить контекст;
- большие файлы неудобно читать и обновлять;
- изменения одной строки требуют работы с большим документом.

## Requirements

Провести аудит и предложить структуру:

### Task documentation

Рассмотреть разделение:

- task file — только цель, требования, acceptance criteria, текущий статус;
- updates/log file — история handoff, обсуждения, изменения статуса.

### Team chat

Рассмотреть переход от одного большого файла:

`docs/team-chat.md`

к структуре с дневными или тематическими логами:

`docs/team-chat/`

Цель — хранить историю, но не требовать чтения всего архива.

### Task index

Рассмотреть разделение:

- README — короткий индекс;
- backlog — очередь;
- archive — завершённые задачи;
- history — изменения.

## Result format

# DOCUMENTATION AUDIT

## NOW

Что мешает работе сейчас:

- проблема;
- влияние;
- размер S/M/L;
- риск Low/Medium/High;
- рекомендация.

## NEXT

Что желательно изменить:

- проблема;
- влияние;
- размер;
- риск;
- рекомендация.

## LATER

Что можно оставить.

## DO NOT TOUCH

Что не стоит переносить или усложнять.

## Critical rules

Не делать реорганизацию ради красоты.

Каждое изменение должно улучшать:

- скорость восстановления контекста;
- надёжность передачи задач;
- читаемость текущего состояния;
- снижение риска потери истории.

## Not doing

- изменения backend/frontend;
- изменение продуктовой логики;
- переписывание всех документов без необходимости.

## Acceptance criteria

- [ ] Есть предложение новой структуры docs.
- [ ] Отдельно определено, что является current state, а что history.
- [ ] Есть план миграции без потери истории.
- [ ] Указано, какие документы не требуют изменения.
