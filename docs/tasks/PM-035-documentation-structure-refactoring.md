# PM-035 — Documentation Structure Refactoring

**Title:** уменьшить технический долг документации и ускорить восстановление контекста команды.

**Status:** done — аудит и план готовы; перенос файлов отдельно не начат. **Priority:** P2. **Owner:** Марк / Product Manager.

**Agent:** Марк. **Role:** Product Manager. **Scope:** структура документации, процессы работы команды; без кода и изменений приложения.

**Recommended model:** Sol. **Recommended reasoning:** Medium.

**Reason:** текущая документация стала большим рабочим хранилищем истории. Нужно отделить текущее состояние от журналов изменений, чтобы восстановление контекста было быстрее и надёжнее.

## Goal

Сделать структуру docs удобной для ежедневной работы команды и восстановления сессии после потери контекста.

## Problem

Сейчас некоторые документы одновременно содержат:

- актуальное состояние;
- историю изменений;
- обсуждения;
- инструкции процесса.

Из-за этого:

- сложно быстро восстановить контекст;
- большие файлы неудобно читать и обновлять;
- изменения одной строки требуют работы с большим документом.

## Requirements

Провести аудит и предложить структуру:

### Task documentation

Рассмотреть разделение:

- task file — только цель, требования, acceptance criteria, текущий статус;
- updates/log file — история handoff, обсуждения, изменения статуса.

### Team chat

Рассмотреть переход от одного большого файла:

`docs/team-chat.md`

к структуре с дневными или тематическими логами:

`docs/team-chat/`

Цель — хранить историю, но не требовать чтения всего архива.

### Task index

Рассмотреть разделение:

- README — короткий индекс;
- backlog — очередь;
- archive — завершённые задачи;
- history — изменения.

## Result format

# DOCUMENTATION AUDIT

## NOW

Что мешает работе сейчас:

- проблема;

- размер S/M/L;
- риск Low/Medium/High;
- рекомендация.

## NEXT

Что желательно изменить:

- проблема;
- влияние;
- размер;
- риск;
- рекомендация.

## LATER

Что можно оставить.

## DO NOT TOUCH

Что не стоит переносить или усложнять.

## Critical rules

Не делать реорганизацию ради красоты.

Каждое изменение должно улучшать:

- скорость восстановления контекста;
- надёжность передачи задач;
- читаемость текущего состояния;
- снижение риска потери истории.

## Not doing

- изменения backend/frontend;
- изменение продуктовой логики;
- переписывание всех документов без необходимости.

## Acceptance criteria

- [x] Есть предложение новой структуры docs.
- [x] Отдельно определено, что является current state, а что history.
- [x] Есть план миграции без потери истории.
- [x] Указано, какие документы не требуют изменения.

### Что считать текущим состоянием

| Источник | Что там должно быть видно сразу | Что остаётся историей |
| --- | --- | --- |
| `status.md`, `roadmap.md` | Текущие приоритеты, блокеры, реальные claims, следующий шаг | Прошлые срезы — в changelog и задачах, без копирования в статус |
| `product-context.md`, `decisions/` | Принятые продуктовые границы и ссылки на решения | Причины и прежние альтернативы остаются в самих decision files |
| Карточка `tasks/PM-XXX.md` | Цель, требования, критерии, статус/владелец, последнее evidence и ссылка на журнал | Подписанные обсуждения, handoff, прежние состояния и QA-прогоны в журнале, если он создан |
| `tasks/README.md`, `ai-team.md`, `team.md` | Краткий индекс, маршрут восстановления, действующие правила и роли | Датированные изменения процесса в changelog и архиве; не в начале ежедневного входа |
| `team-chat.md` | Куда писать сегодня и где последние адресованные сообщения | Неизменённые дневные логи и старые разговоры по ссылкам |
| `changelog.md` | История релизов и существенных решений, читается по нужной дате/задаче | Весь прежний текст сохраняется, полный перечень не нужен для каждого входа |

- Не делать новый backlog с собственными приоритетами, не переставлять работу Дениса/Игоря/Бориса и не затрагивать приложение.

### План безопасного переноса — отдельная работа после аудита

1. Записать текущие SHA, список исходных файлов, внешние/внутренние ссылки и активные claims. Если кто-то пишет в те же файлы, согласовать окно и область. Не превращать перенос в правку содержания.
2. **Скопировать историю дословно прежде сокращения входа**: исходный `team-chat.md` и историческую нижнюю часть `tasks/README.md` в датированные архивы; проставить в коротких старых путях ссылки на архив и дату границы. Для дневных файлов сохранить автора, адресата, время, последовательность, включая критику и нерабочие реплики. Если есть deep links на старые заголовки, проверить и оставить рабочий указатель; GitHub сам не перенаправляет якоря в новый файл.
3. Создать `tasks/workflow.md` из действующих правил. Сверить его с `ai-team.md` и `team.md`, указать один канонический источник каждого правила. Оставить `tasks/README.md` как короткий индекс с **точно теми же IDs/status/claims**, проверить переходы по всем ссылкам.
4. Опробовать дневной чат и короткую карточку+лог на **одной новой** задаче. Сравнить количество прочитанных файлов/байтов и время восстановления; убедиться, что статус, acceptance, последнее QA evidence и адресованные сообщения находятся за максимум двумя короткими входными документами плюс самой задачей. При конфликте обновления остановить перенос и сохранить обе версии.
5. Только после проверок обновить `ai-team.md`, `team.md`, `product-context.md` (маршрут чтения), `status.md` и changelog; занести новые канонические пути в задачи. Если указатели или история не сходятся, восстановить прежние файлы из зафиксированных SHA и повторить с меньшим объёмом.

**Граница полномочий:** нынешний перечень редактируемых PM-путей в `team.md` содержит `docs/team-chat.md`, но не `docs/team-chat/*`. PM-035 разрешает **предложить** эту структуру, а не открывает право переноса в новый каталог. Перед исполнением этого этапа нужно явно определить исполнителя/разрешённый scope; этот аудит не меняет правила доступа. До миграции команды продолжают пользоваться текущими путями. Нового продуктового решения о видимости данных или фичах здесь нет.
