# PM-029 — Два независимых PARROT-сеанса в одном управляемом браузере

**Title:** дать Борису два одновременно авторизованных тестовых входа в PARROT через два разных origin.
**Status:** in progress — Игорь взял реализацию; независимая QA Бориса после релиза. **Priority:** P1.
**Owner:** Игорь / Developer; Марк / PM координирует, Борис / QA принимает результат.
**Agent:** Игорь. **Role:** Developer. **Scope:** frontend Worker, настройка второго Cloudflare origin и обязательная backend-проверка по account ID; действующий origin и обычные auth-права сохраняются.
**Recommended model:** Sol. **Recommended reasoning:** High. **Reason:** два origin, backend allowlist, доверие между Worker и backend, cookies и CSRF требуют совместной проверки без ослабления обычной авторизации.
**Model check:** security scope требует High; разделяю backend guard, Worker forwarding и настройки инфраструктуры, проверяю каждый границей CI и negative tests.

## Goal

Борис в одном доступном ему Cloud Chrome открывает две вкладки с разными адресами PARROT и самостоятельно выполняет весь цикл: аккаунт A пишет хозяину, аккаунт B получает и отвечает, A видит ответ. После первоначального входа Алексею не нужно переключать аккаунты или управлять второй вкладкой.

## Problem

[PM-016](PM-016-qa-second-session-access.md) заблокирована: инструменты Бориса видят только один Cloud Chrome, вкладки `parrot669.com` используют общую cookie-сессию. Встроенный браузер Desktop, в котором Алексей вошёл под `qa`, не появился среди доступных Борису браузеров. Выход/вход в одном origin стирает первое состояние и не позволяет пройти обмен самостоятельно. Поэтому PM-003 и часть PM-024/010/028 остаются без двухсторонней независимой QA.

## User

Борис / QA; после первого входа он должен самостоятельно управлять обоими тестовыми участниками.

## Value

Снимаем зависимость регрессии переписки и auth от ручного переключения аккаунтов Алексеем.

## Solution — гипотеза для проверки разработчиком

Поднять второй стабильный HTTPS origin для **того же** frontend Worker и **того же** production backend, например `qa.parrot669.com` рядом с `parrot669.com`. Через него Host, Search, Messages и `/api/*` должны работать **только** для подтверждённых аккаунтов `qa` и `lelik`; backend обязан проверять это условие. Это не отдельная база и не QA-обход авторизации. Перед выбором имени убедиться, что он не занят и разрешён действующей конфигурацией Cloudflare.

Основание в текущем `main`: `AuthRoutes.scala` выдаёт `parrot_session` с `Path=/; HttpOnly; SameSite=Lax`, без `Domain`, то есть cookie должна быть привязана к конкретному host. `public/assets/host.js` использует `credentials: "same-origin"`, а `src/index.js` проксирует cookie к `api.parrot669.com` и возвращает `Set-Cookie`. Это **предположение об изоляции**, а не подтверждённый live-тест двух origin.

Если alias уже существует, использовать его только после добавления и проверки обязательного backend-ограничения. Исполнитель выбирает технический способ маршрутизации после проверки текущего Cloudflare и auth, не добавляя в продукт переключатель или бэкдор.

## Requirements

- Оба origin открываются одновременно в одном Cloud Chrome, без автоматического редиректа на общий host, и работают с одной и той же базой PARROT.
- **Обязательная backend-защита второго origin:** после обычной аутентификации разрешать там только стабильные account ID, соответствующие существующим подтверждённым аккаунтам `qa` и `lelik`, а не совпадение отображаемого имени/вводимого username. Любой другой аккаунт и анонимный запрос к данным второго origin — отказ без выдачи персональных данных. Логин проверять после валидации пароля и принадлежности аккаунта к allowlist; создание новых аккаунтов/восстановление/смена пароля через QA origin не расширяют allowlist.
- Backend должен достоверно отличать запросы второго origin от обычного: Worker передаёт признак по защищённому каналу с серверным секретом/эквивалентной проверяемой аттестацией; секрет хранится в конфигурации Cloudflare/Railway, не в браузере и не в репозитории. Недостаточно доверять `Origin`, `Host` или клиентскому `X-...`: их можно подделать. При отсутствующей/неверной аттестации QA-маршрут закрывается; обычный `parrot669.com` сохраняет текущие права и авторизацию.
- Проверить все API на QA origin, включая public/search, Host, auth, messaging и маршруты смены состояния; не ограничиваться UI и одним `/api/auth/me`. Если часть анонимных запросов технически необходима для отображения формы входа, она не выдаёт QA-данных и описана явно.
- Вход под A на основном адресе и под B на втором сохраняется в двух вкладках; refresh и навигация Search → Messages → Host остаются на соответствующем origin. Проверить относительные/абсолютные ссылки и email/auth redirects, если они участвуют в сценарии.
- `/api/auth/me`, `/api/messaging/*` и остальные необходимые для сценария API получают **свою** cookie; Worker не ослабляет проверку Origin/CSRF и не принимает чужую cookie.
- Logout A не сбрасывает B; повторный вход A не меняет B; сообщения между участниками видны в общей backend-базе.
- Никаких общих паролей, session tokens, cookie values в репозитории, URL, логах задачи или переписке. Входы остаются обычными подтверждёнными тестовыми аккаунтами.
- Если host-only cookie или Worker на втором origin ведут себя иначе, записать причину и предложить эквивалентный вариант изоляции. Не вводить скрытую impersonation-функцию и не отключать проверки для production.

## Acceptance criteria

- [ ] Разработчик указал адрес второго origin, frontend/backend commit, Cloudflare/Railway deployment и проверил, что оба адреса указывают на одну актуальную PARROT-версию и backend.
- [ ] На втором origin только аккаунты `qa` и `lelik` проходят backend allowlist; вход третьего подтверждённого аккаунта, анонимный доступ к QA API и подмена клиентских `Origin`/`Host`/заголовка не открывают QA-доступ. Защита проверена на backend, а не только скрытой кнопкой или правилом Worker.
- [ ] Основной `parrot669.com` работает для обычных аккаунтов как до изменения; никакой QA-привилегии на основном origin не появилось.
- [ ] Борис видит обе вкладки в **своём** browser API и после однократного безопасного входа видит `/api/auth/me` как A/B соответственно; секреты и cookie не попадают в отчёт.
- [ ] Одновременно A → сообщение на объект B → ответ B → ответ виден A; refresh обоих не смешивает имена, диалоги и непрочитанное.
- [ ] Logout A оставляет B авторизованным, и наоборот; повторный login не влияет на другую вкладку. Проверка проводится только после того, как известен безопасный способ вернуться в тестовые аккаунты.
- [ ] На втором origin нет нового публичного режима, другого backend, расширенного доступа, сломанной Origin/CSRF-проверки или утечки авторизации в URL.

## Alternatives

Два browser state через ChatGPT Desktop/extension — пока недоступны агенту, хотя браузер пользователя открыт. Повторный ручной logout/login — требует участия Алексея и прерывает тест. Если разработчик подтвердит работающий существующий alias с изоляцией cookie, отдельный deploy не нужен.

## Rejected

QA-only master password, impersonation и отключение auth/CSRF в production; frontend-only allowlist по username или доверие клиентскому заголовку как доказательству QA origin; сохранение session cookie в localStorage или передача её Борису в чат.

## Success criteria

Полный самостоятельный PM-003 и двухаккаунтные проверки PM-024/010/028 выполняются Борисом без действий Алексея между первым сообщением и ответом.

## Not doing

Новая модель пользователей, staging-данные вместо проверяемого production, расширение публичного профиля или изменение бизнес-логики сообщений.

## Dependencies / Unblock

[PM-016](PM-016-qa-second-session-access.md) — QA-блокировка; PM-003, PM-024, PM-010 и PM-028 — зависимые приёмки. Два уже существующих подтверждённых тестовых аккаунта `qa` и `lelik`, разрешённых backend allowlist; первая авторизация на втором origin может потребовать однократного безопасного входа.
