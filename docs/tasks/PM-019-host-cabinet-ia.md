# PM-019 — Контракт кабинета владельца

**Title:** определить навигацию и границы кабинета без переписывания существующих функций.
**Status:** planned — NEXT, продуктовый контракт; реализации пока нет. **Priority:** P2. **Owner:** Марк / Product Manager (контракт).
**Agent:** Марк. **Role:** Product Manager. **Scope:** карта пользовательских разделов, переходов и терминов; только документация.
**Recommended model:** Luna. **Recommended reasoning:** Medium. **Reason:** нужно сверить несколько существующих экранов и их права, не проектируя новую архитектуру приложения.
**Model check:** Марк проверяет достаточность перед началом отдельного анализа/фиксации контракта; этот backlog не является claim реализации. Повышение по D005 при доказанной необходимости.

## Goal
Владелец понимает, где управлять объектами, датами, сообщениями и входом, и не теряет контекст при переходах.

## Problem
Сейчас /host.html содержит авторизацию, создание объектов, доступность, iCal и настройку входящих сообщений; переписка живёт в /messages.html. Предложенная Алексом структура Dashboard / Properties / Availability / Contacts / Profile / Account пока не соотнесена с фактическими действиями. Шесть пустых вкладок усложнят MVP.

## User
Владелец, добавляющий жильё и отвечающий гостю.

## Value
Меньше блуждания между действиями и понятный путь от добавления объекта к доступным ночам и контакту.

## Solution
Подготовить компактную карту существующих действий, разделов и переходов; согласовать минимальную навигацию с владельцем до [PM-020](PM-020-host-cabinet-navigation.md). Физические маршруты (одна страница/несколько страниц) исполнитель выбирает после продуктового контракта.

## Requirements
- Нанести на карту сегодняшние /host.html, /messages.html, вход/выход и восстановление, объекты, периоды, ручные блокировки, iCal/проверку, настройку приёма сообщений.
- Для Dashboard, Properties, Availability, Contacts, Profile, Account указать: какое действие существует сегодня; его вход и выход; где виден результат; что ещё только предложение. Не показывать раздел Profile как готовую функцию до появления PM-021.
- Решить минимальный набор видимых разделов и мобильную схему переходов. Dashboard без доказанной пользы может быть точкой входа с существующими данными либо не входить в первую поставку.
- Зафиксировать работу без объекта, с несколькими объектами, без внешнего календаря, при выключенных сообщениях и при возврате из переписки. Войти/выйти/восстановление остаются действиями Account; аккаунт не смешивать с публичным профилем.
- Не терять выбранный объект/состояние формы при разумных переходах; конкретное правило сохранения несохранённого ввода согласовать явно.
- Отметить пересечения с PM-001/003/004/005/007 и доступной мобильной QA-средой PM-015. Содержание PM-002 не предрешать.

## Acceptance criteria
- [ ] Есть таблица «существующее действие → согласованный раздел → переход → источник данных» с пометкой для ещё не существующих элементов.
- [ ] Выбран один минимальный первый этап, понятны пустые/неавторизованные состояния и возврат из Messages.
- [ ] Зафиксирован способ навигации на desktop и телефоне, а также правило для несохранённых изменений.
- [ ] Алексей подтвердил предложенный продуктовый контракт или оставил конкретные правки; после этого PM-020 можно назначить исполнителю.

## Alternatives
Оставить текущую /host.html и улучшить якоря; структурировать существующий экран; отдельные страницы для каждого действия. Выбор по сложности основного пути и мобильной проверке.

## Rejected
Реализовывать все шесть разделов как пустые обещания или переносить логику доступности/верификации ради новой оболочки.

## Success criteria
В QA владелец проходит «объект → даты → включить контакт → ответ» без потерянного контекста; в пилоте меньше остановок на навигации. Числового порога пока нет.

## Not doing
Новый backend, новый trust badge, публичные данные, фото, Instagram, обещание удаления аккаунта как готовой функции или редизайн гостевого поиска.
