# PM-019 — Контракт кабинета владельца

**Title:** определить навигацию и границы кабинета без переписывания существующих функций.
**Status:** done — D009 подтверждён владельцем; PM-020 уже реализован и находится в review. **Priority:** P2. **Owner:** Марк / Product Manager (контракт).
**Agent:** Марк. **Role:** Product Manager. **Scope:** карта пользовательских разделов, переходов и терминов; только документация.
**Recommended model:** Luna. **Recommended reasoning:** Medium. **Reason:** нужно сверить несколько существующих экранов и их права, не проектируя новую архитектуру приложения.
**Model check:** Luna / Medium достаточно для анализа действующих экранов и фиксации IA; техническая реализация не входит в эту задачу.

## Goal
Владелец понимает, где управлять объектами, датами, сообщениями и входом, и не теряет контекст при переходах.

## Problem
Сейчас /host.html содержит авторизацию, создание объектов, доступность, iCal и настройку входящих сообщений; переписка живёт в /messages.html. Предложенная Алексом структура Dashboard / Properties / Availability / Contacts / Profile / Account пока не соотнесена с фактическими действиями. Шесть пустых вкладок усложнят MVP.

## User
Владелец, добавляющий жильё и отвечающий гостю.

## Value
Меньше блуждания между действиями и понятный путь от добавления объекта к доступным ночам и контакту.

## Solution
Подготовить минимальную навигацию из существующих действий и зафиксировать ее в [предложении D009](../decisions/D009-host-cabinet-ia.md). Для первой версии сохранить существующие страницы/URL; PM-020 получает только frontend-навигацию и состояние переходов, без миграции backend.

## Requirements
- Нанести на карту сегодняшние /host.html, /messages.html, вход/выход и восстановление, объекты, периоды, ручные блокировки, iCal/проверку, настройку приёма сообщений.
### Принятая IA (D009)

| Область | Где живёт действие | Правило первой версии |
| --- | --- | --- |
| Properties | /host.html, карточки объектов | Добавление, список, характеристики и удаление объектов. Для пустого аккаунта /host.html сразу предлагает добавить первый объект. |
| Availability | В раскрытой карточке конкретного объекта | Периоды PARROT, ручные закрытия, Airbnb iCal и проверка календаря принадлежат этому объекту. Отдельной глобальной страницы Availability нет. |
| Contacts | Настройка на /host.html; входящие диалоги на /messages.html | Переключатель новых сообщений действует на профиль владельца; Inbox и ответы живут на Messages. Не смешивать входящие обращения с публичными внешними контактами. |
| Account | Верхняя панель host/messages и формы входа | Email/username, войти/создать аккаунт/выйти; восстановление доступно через /recover.html. Это доступ к аккаунту, не публичный профиль. |
| Dashboard | Не выделять отдельный экран | Отдельных показателей/аналитики пока нет; не создавать пустую вкладку. /host.html — рабочий вход в Properties. |
| Profile | Не показывать в навигации первой версии | Личных редактируемых/публичных полей сверх существующей идентичности пока нет; scope отдельно проходит через PM-021/022. |

Глобальная навигация первой версии остаётся Search / Host / Messages с текущими URL. Внутри Host не добавлять вкладки Availability, Contacts, Profile и Account: сначала разделы Properties и Messages, а доступность и контактные настройки показываются там, где их действие относится к объекту или переписке.

- Описать переходы и состояния desktop/mobile поверх существующей навигации; не менять гостевой Search.
- Для нового аккаунта после входа пустое состояние ведёт к созданию объекта; для одного/нескольких объектов список остаётся на /host.html. Нет подключённого Airbnb — PARROT availability всё равно доступна.
- Возврат из Messages ведёт обратно в Host; расширенные карточки/позиция страницы восстанавливаются в пределах навигации той же вкладки. Несохранённый ввод не теряется молча: перед уходом предложить остаться или подтвердить сброс.
- На мобильном оставить понятные тач-цели для трёх верхних направлений; не проектировать боковое меню/сложную вложенную навигацию без доказанной нужды. Настоящий iPhone ретест зависит от PM-015.
- Проверить пересечения с PM-001/003/004/005/007. Внешний линк и правила его публичности остаются в PM-002 — D009 их не меняет.

## Acceptance criteria

- [x] Предложена минимальная первая версия навигации: текущие Search / Host / Messages без пустых вкладок.
- [x] Описаны состояния пустого аккаунта/объекта, несколько объектов, отсутствие Airbnb, вход/выход и возвращение из Messages; несохранённый ввод не сбрасывается молча.
- [x] Владелец подтвердил D009. Последовательность кабинета: PM-020 → PM-021 → PM-022.

## Alternatives
Оставить текущую /host.html и улучшить якоря; структурировать существующий экран; отдельные страницы для каждого действия. Выбор по сложности основного пути и мобильной проверке. Рекомендация PM: сохранить текущие страницы и углубить содержание карточки объекта.

## Rejected
Реализовывать все шесть разделов как пустые обещания или переносить логику доступности/верификации ради новой оболочки.

## Success criteria
В QA владелец проходит «объект → даты → включить контакт → ответ» без потерянного контекста; в пилоте меньше остановок на навигации. Числового порога пока нет.

## Not doing
Новый backend, новый trust badge, публичные данные, фото, Instagram, обещание удаления аккаунта как готовой функции или редизайн гостевого поиска.
