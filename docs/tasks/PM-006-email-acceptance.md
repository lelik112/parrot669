# PM-006 — Приёмка писем и восстановления доступа

**Title:** закрыть непроверенные пользовательские сценарии реальных email.

**Status:** planned. **Priority:** P1. **Owner:** не заявлен.

**Agent (ожидаемый):** Борис / QA; claim не подтверждён. **Recommended model:** Sol. **Recommended reasoning:** Medium. **Reason:** нужно проверить три реальных почтовых сценария, доставку, одноразовый token и поведение сессий, при этом отделяя письма провайдера от фактического получения пользователем.

**Model check:** подтвердить при назначении; отсутствие разрешённого ящика или аккаунта фиксируется как blocker.

**Area:** QA / auth / messaging email. **Updated:** 2026-09-24, Марк / PM.

## Goal

Подтвердить, что пользователь получает нужное письмо и может завершить действие.

## Problem

Ссылка восстановления и настройки уведомлений проверены частично; реальная доставка и полный цикл не закрыты независимым QA. Принятие письма провайдером не означает получение пользователем.

## Context

[QA 23.09](../qa/2026-09-23/PARROT669-QA-2026-09-23.md): BUG-005 закрыт как отсутствие видимого пути восстановления, не как полный reset. Backend/CI-проверки уже есть; не переоткрывать закрытый UI-дефект только из-за оставшегося QA.

## Requirements

- Использовать разрешённые тестовые аккаунты и ящики. Раздельно записывать три сценария: новая регистрация/подтверждение; восстановление; уведомление о непрочитанном сообщении.
- Для восстановления пройти запрос → получение → ссылка → новый пароль → вход; проверить предусмотренную недействительность старых сессий и повторного использования ссылки.
- Для уведомления подтвердить получение адресатом и переход в нужный диалог; отсутствие текста сообщения/чужих контактов в письме.
- В ограниченном сценарии проверить настройку отказа от уведомлений и прочитанное сообщение до отправки. Отдельно отметить уже находившееся в отправке письмо, если это влияет на наблюдение.
- Зафиксировать язык, обычную папку/спам и задержку; не объявлять письмо доставленным по одному логу провайдера.

## Acceptance criteria

- [ ] Каждый из трёх сценариев имеет отдельный pass/fail/blocked с evidence.
- [ ] Подтверждение регистрации и полный reset завершены тестовым пользователем; старые данные входа/сессии и использованная ссылка дают предусмотренный результат.
- [ ] Письмо о сообщении получено нужным адресатом, переход работает, содержимое сохраняет заявленную приватность.
- [ ] Проверенные opt-out/read-сценарии описаны; непроверенные языки/границы не отмечены прошедшими.
- [ ] Учётные данные, reset/verification tokens и приватный текст не попали в репозиторий; тестовое состояние восстановлено.

## Not doing

Новая почтовая архитектура, смена провайдера, добавление webhook, изменение паролей реальных пользователей, правки кода в роли QA/PM.

## Dependencies

Доступ к разрешённым ящикам и аккаунтам; для уведомлений — рабочий сценарий PM-003. Если любой доступ отсутствует, записать конкретный blocker и продолжить независимые доступные части, не переоформляя всю фичу как сломанную.

До этого прохода реальные сценарии из постановки независимо не закрыты. Новый результат ожидается.
