# PM-021 — Личный профиль владельца

**Title:** определить и затем реализовать редактируемые данные владельца отдельно от учётной записи.
**Status:** planned — LATER, состав новых полей и публикация не согласованы. **Priority:** later. **Owner:** исполнитель не назначен.
**Agent:** будущий Developer после отдельного решения; **Role:** Developer. **Scope:** приватное редактирование profile, существующая авторизация; не реализация публичных контактов.
**Recommended model:** Sol. **Recommended reasoning:** High. **Reason:** новые поля могут затронуть backend schema/API и приватность; текущие account/profile уже имеют разные назначения.
**Model check:** будущий исполнитель анализирует выбранные поля, доступ и текущие API перед claim; повышение только по D005.

## Goal
Владелец может понять и при необходимости изменить данные, которые характеризуют его как хозяина, отдельно от email/пароля/сессии.

## Problem
Имя/метка вводится при регистрации, но ясного интерфейса управления личным профилем нет. Алекс предложил фото, «о себе», Instagram и контакты; их нужность для MVP и правила раскрытия пока не доказаны.

## User
Владелец жилья, потенциальный гость, который увидит только отдельно разрешённую публичную часть.

## Value
Данные владельца можно исправлять, а происхождение публичного имени остаётся понятным.

## Solution
Сначала согласовать минимальные поля, границы приватности и отдельные разрешения на публикацию; после этого дать авторизованному владельцу редактирование через существующий profile/account ownership. MVP-кандидат — уже существующий display name. Фото, About, Instagram и внешние контакты оцениваются отдельно, не включаются молча.

## Requirements
- Описать уже существующие account email/username и profile display name, источник имени в поиске и публичном JSON; не создавать вторую конкурирующую сущность хозяина.
- Для каждого нового поля зафиксировать цель, формат/лимиты, право редактирования, приватность по умолчанию, удаление/изменение, показ в поиске/профиле и необходимость согласия до реализации.
- Account оставляет email, пароль/восстановление, выход и вопросы конфиденциальности; не обещать кнопку delete account, если отдельного рабочего сценария пока нет.
- Для фото отдельно решить происхождение, хранение и согласие; не копировать фото/описание Airbnb и не требовать фотографию для добавления жилья.
- Не менять начальное состояние приёма сообщений; внешние контакты не обходят выбранные правила согласия и блокировки.

## Acceptance criteria
- [ ] Утверждена таблица полей с приватностью по умолчанию и источником каждого публичного значения, либо новые поля явно отложены.
- [ ] У авторизованного владельца есть проверенный путь изменить выбранные поля; другой аккаунт не может их читать или менять без согласованного публичного разрешения.
- [ ] Гостевой поиск, текущий backend public profile и сообщения не начинают показывать email, точный адрес, iCal URL или новые контакты по умолчанию.
- [ ] QA проверяет сохранение, reload, ошибки и отказ от публичного показа; релиз отдельно от продуктового контракта.

## Alternatives
Использовать существующий display name без новых полей; добавить ограниченный About; полноценная карточка с фото/ссылками. Выбор после пилота и согласования privacy.

## Rejected
Автоматически считать поле регистрации публичным согласием на все будущие данные; обязательный Instagram/фото; «Trusted host» без проверки.

## Success criteria
Владелец понимает и контролирует, какие сведения сохранены и какие видны гостю; влияние на контакт оценивается в PM-008, а не по числу заполненных полей.

## Not doing
Публичная страница (PM-022), верификация Instagram, собственный рейтинг, бронирование, обмен контактами без согласия.

## Dependencies
Навигационный контракт PM-019, данные пилота PM-008 и согласованная privacy-модель. PM-020 может выйти раньше без этой задачи. Отдельно согласовать scope перед исполнением.

## Evidence
У backend уже есть profile identity и публичный JSON; поля нового профиля и показатели пользы не подтверждены.
