# PM-030 — Разгрузить QA-хвост и подготовить следующий продуктовый этап

**Title:** синхронизировать реальный статус QA-очереди и подготовить следующий запуск после текущей волны тестирования.

**Status:** planned — owner поручит Марку. **Priority:** P1. **Owner:** Марк / Product Manager.

**Agent:** Марк. **Role:** Product Manager. **Scope:** только продуктовая документация, приоритеты, backlog и координация; без кода и инфраструктуры.

**Recommended model:** Sol. **Recommended reasoning:** Medium.

**Reason:** нужно свести много параллельных in review задач, зависимости PM-016/029 и определить следующий продуктовый шаг без запуска лишней разработки.

## Goal

Сделать так, чтобы после разблокировки двухсессионного QA команда не продолжала бесконтрольно наращивать in review, а быстро закрыла критичный хвост и получила понятный следующий этап разработки.

## Context

На 2026-09-25 в реестре накопился большой хвост задач in review. PM-029 должна снять главный двухаккаунтный QA-блокер PM-016. Разработчики выпустили несколько связанных P1/P2 изменений быстрее, чем Борис успевает их принять.

Одновременно уже намечен следующий продуктовый слой: public host profile (PM-022), trust terminology, How it works, FAQ и последующая перестройка homepage. Запускать его в код прямо сейчас не требуется; сначала нужно понять, что реально закрывается после PM-029.

## Requirements

1. Сверить docs/tasks/README.md, task files, status.md, roadmap.md и свежие handoff/QA записи.
2. Исправить рассинхрон между task index, status и roadmap, если он есть.
3. Составить **одну приоритетную QA-очередь** после разблокировки PM-016/029:
   - сначала P1 основной пользовательский путь;
   - затем P2 regression/UI;
   - отдельно отметить то, что всё ещё требует участия Алексея или внешней среды.
4. Для каждой in review задачи определить одно из состояний:
   - можно закрыть после уже имеющегося evidence;
   - нужен конкретный короткий ретест;
   - нужен двухаккаунтный сценарий;
   - нужен mobile/Safari/email/Airbnb внешний ресурс;
   - реально есть незакрытый дефект и нужна разработка.
5. Не назначать новую крупную dev-фичу только потому, что разработчик свободен. До первых результатов новой QA-волны держать свободный dev capacity под быстрые bugfix.
6. Подготовить **следующий продуктовый пакет без реализации**:
   - PM-022 public host profile: актуализировать зависимости после PM-002/021 и довести контракт до состояния, которое можно отдать на approval;
   - создать/актуализировать отдельные задачи на trust terminology, How it works и FAQ;
   - homepage restructuring держать после этих контрактов;
   - legal/privacy оставить pre-launch, если нет новой причины поднять раньше.
7. После первой QA-волны дать Алексею короткую рекомендацию: какую **одну** следующую dev-задачу запускать и почему.
8. Для каждой новой dev-задачи указать Recommended model / reasoning по docs/ai-team.md.

## Acceptance criteria

- [ ] docs/tasks/README.md, status.md и roadmap.md не противоречат друг другу по активным задачам.
- [ ] Есть упорядоченная QA-очередь с понятными блокерами и следующим действием.
- [ ] Понятно, какие задачи должны закрыться сразу после PM-029/016.
- [ ] Свободные разработчики не получают новую крупную работу до первых результатов QA без явного решения владельца.
- [ ] PM-022 доведена до актуального product contract / списка открытых решений.
- [ ] Trust terminology, How it works и FAQ представлены отдельными задачами или явно привязаны к существующим, без реализации.
- [ ] Марк сообщает Алексею: текущий QA bottleneck, что разблокировалось, что осталось blocked и одну рекомендуемую следующую dev-задачу.

## Not doing

- Самостоятельное выполнение QA вместо Бориса.
- Запуск PM-022/FAQ/How it works в разработку без отдельного решения Алексея.
- Создание большого количества задач ради красивого backlog.
