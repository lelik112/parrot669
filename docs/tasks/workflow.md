**Agent:** Марк. **Role:** Product Manager. **Change:** действующие правила вынесены из [старого README](README-history-2026-09-25.md) в рамках [PM-035](PM-035-documentation-structure-refactoring.md). **Related task:** PM-035.

Роли и авторство — в [team.md](../team.md), рекомендации моделей — в [ai-team.md](../ai-team.md), продуктовые решения — в [product-context.md](../product-context.md) и [decisions](../decisions/README.md).

## PM-отчёт владельцу продукта

После создания или изменения задач, а также в каждом ответе о статусе/backlog PM сообщает короткий статус затронутых задач и полный актуальный список открытых задач, отсортированный по **NOW → NEXT → LATER**, затем по **P0 → P1 → P2**. По каждой задаче указываются статус, фактический claim/исполнитель (или «не назначена»), причина отсутствия назначения/claim, и рекомендованные model/reasoning из task file. Для blocked задач указываются блокер и следующий шаг.

`Owner` или ожидаемый исполнитель в задаче не считается фактическим назначением без явного claim/подтверждения. Если задача просто planned и пока никем не взята, так и писать; Markdown в репозитории не уведомляет агента. Done/rejected задачи не включаются в открытый backlog. Отсутствующие рекомендации не выдумываются.

## Claim и передача

1. Обновить основную ветку документации и проверить актуальный `Owner`, журнал и зависимости. Не считать чужую старую ветку свободной задачей.
2. До реализации указать **Agent, Role, Scope**, статус, время UTC и ближайший шаг по [формату team.md](../team.md). Обновить индекс. Зафиксировать claim в репозитории и убедиться, что текущая общая версия действительно содержит его. **Подтверждённый claim в согласованном scope означает старт работы: отдельного одобрения Марка после claim нет.** Исполнитель продолжает до результата, QA handoff или конкретного блокера; Алексей не переносит сообщения между чатами ради каждого шага.
3. У задачи один ответственный за координацию. Если claim уже есть, сначала записать предложение о разделении, дождаться ответа и назвать границы соисполнителей. Конфликт двух claims решается явно; не перезаписывать чужое имя молча.
4. Вопросы, предложения, блокировки и ответы добавлять в **Discussion / Updates** карточки либо, если карточка уже ссылается на `logs/PM-XXX.md`, в этот журнал. **Текущий статус, owner, acceptance и последний следующий шаг остаются в карточке**. Для обновления статуса обязательно указывать **Agent, Role, Change, Related task**, дату и следующий шаг; перед началом — также Scope. Для короткого обсуждения: `YYYY-MM-DD HH:MM UTC — Имя / роль — вопрос или ответ — следующий шаг`. Адресат указывается текстом, без придумывания GitHub-аккаунта.
5. При смене scope отметить затронутые задачи и продуктовый контракт. Новое продуктовое решение фиксирует PM; технический выбор внутри согласованных требований остаётся за разработчиком. К Марку передавать только конфликт claims/приоритетов, изменение продуктового контракта, выход за scope или блокер, который исполнитель сам не решает. QA может записать FAIL прямо в задаче; разработчик в своей назначенной области может исправить его без дополнительного цикла «QA → Алексей → PM → Алексей → Developer», если нет нового продуктового решения.
6. По завершении разработки указать репозиторий, PR/commit, что изменилось, проверки, статус публикации и оставшиеся ограничения; перевести в `in review`. Для изменения без релиза явно написать, что публикация не требуется и почему.
7. QA записывает результат каждого существенного критерия, среду/версию и ссылку на доказательства. `done` — после проверки критериев; наличие кода, зелёного CI или push само по себе не равно приёмке.
8. При остановке оставить понятный handoff: что сделано, что не сделано, блокировка и следующий шаг. После значимого изменения PM обновляет product-context, changelog и decision log с авторством и причинами; status и roadmap согласуются по фактам.

Для параллельных записей сначала подтянуть изменения и разрешить конфликт с сохранением обеих записей. Не использовать force-push и не переписывать чужую историю. Не менять чужую рабочую папку. Отсутствие ответа означает ожидание, а не согласие.

Обычный push документа на `main` сам по себе не будит чаты. Для подтверждённых адресов работает только GitHub comment event в открытом PR с личным включённым trigger [D017](../decisions/D017-pr-inbox-handoffs.md). PM не утверждает, что задание получено, пока нет подписанного ответа. Почасовой PM check-in отдельно читает repo; он не будит остальные чаты.

## Адресные PR inbox — D017 / PM-046

[Список адресов и состояние настройки](../team.md#адресные-pr-inbox). Каждый inbox — docs-only draft PR, оставленный открытым; он не является PR реализации и его не сливают. **Создание PR не включает webhook другого чата.** Агент один раз в своём существующем чате настраивает GitHub `pull_request` trigger на точный repo + номер своего PR с `enable_comments=true`, после чего PM проверяет один настоящий comment → подписанную запись. До этого состояние `prepared`, а не `active`. После включения trigger адресат записывает в PM-046 `enabled` и отправляет Марку в PR #60 адресный комментарий с новым Wake ID; Марк по событию проверяет запись и оставляет один тестовый комментарий в PR адресата. Получатель подписывает результат и сообщает Марку через #60 новым ID; только тогда Марк меняет статус на `active`. Алексей не пересылает тесты между чатами.

1. Марк фиксирует задачу, scope, критерии, приоритет, модель и ожидаемого исполнителя в карточке на `main`. Затем пишет **top-level PR conversation comment** в inbox адресата: отдельные строки `To: <имя>`, `Wake ID: <новый уникальный ID>`, `Related task: docs/tasks/<файл>.md` и короткий следующий шаг. Запись в карточке или коммит без комментария не являются event.
2. Получатель читает исходный комментарий и свежую карточку `main`, проверяет роль, назначение, существующий claim и scope. Если ID уже имеет **его отдельную подписанную запись**, не пишет повторно; простое упоминание ID кем-то другим не считается обработкой. С текущим blob SHA фиксирует один claim/результат/блокер с Agent, Role, Wake ID, UTC и ссылкой на комментарий; при 409 перечитывает. Комментарий не расширяет продуктовый scope. После claim продолжает согласованную работу без нового одобрения PM.
3. По результату агент пишет карточку и при необходимости отправляет отдельный комментарий в [inbox Марка #60](https://github.com/lelik112/parrot669/pull/60) с `To: Марк`, новым Wake ID и той же карточкой. Марк завершает PM-сверку, принимает решение в своей области либо поднимает владельцу продуктовую развилку. Не отвечать в собственном inbox PR, чтобы не создавать петлю.
4. Завершение event run не поддерживает непрерывное фоновое выполнение. Для следующего запуска нужен следующий адресный комментарий. Shared GitHub account и строка `To:` маршрутизируют событие, но не удостоверяют личность автора. Секреты в PR и task card не пишут; повторная доставка одного event и стоимость регулярного использования пока не измерены.

Марк #60 и Игорь #61 проверены в обе стороны; второй отдельный comment снова запустил Игоря. Денис #62 и Борис #63 также `active` после подписанных receipt. Никита #64 также `active` после signed receipt одного теста, но новая продуктовая QA-работа ему не назначается, пока он занят; Алекс #65 `prepared` и попросил не беспокоить. [PM-046](PM-046-github-event-existing-chat-wakeup.md) хранит evidence и ограничения.

## Авторство

Обязательный единый блок **Agent / Role / Change / Related task** для коммита, PR, статуса задачи и changelog определён в [team.md](../team.md). Он применяется независимо от технического Git author.

Каждый использует выбранное имя в Git author и подписи записей, когда доступный способ коммита позволяет задать автора. Не придумывать адрес существующего человека или отдельный GitHub-аккаунт для подписи агента.

Общий авторизованный GitHub-аккаунт и Git author — разные вещи. Если используемый инструмент не позволяет задать author, это ограничение явно отмечается, а имя/роль обязательно остаются в сообщении коммита и документах. Не выдавать `lelik112` за отдельный аккаунт агента. Чужие глобальные Git-настройки не менять.

## Структура постановки

Каждая новая или возобновляемая задача содержит `Title`, `Agent`, `Goal`, `Problem`, `Context`, `Requirements`, `Acceptance criteria`, `Not doing`, `Dependencies`, `Recommended model`, `Recommended reasoning` и `Reason`, плюс Owner/Status, Evidence, `Model check` и Discussion / Updates. Для новой фичи также фиксируются `User`, `Value`, `Solution`, `Alternatives`, `Rejected`, `Success criteria`. Завершённые задачи не меняются задним числом лишь ради рекомендации; для in-review рекомендация адресуется только следующему QA этапу. До основной работы исполнитель делает model check. Если мощности недостаточно — записывает, какой объём требует увеличения и почему, предлагает вариант и ждёт решения владельца продукта согласно [D005](../decisions/D005-ai-team-model-guidance.md).

Критерии реализации и полезность различаются: прохождение проверки показывает корректность фичи, а реальные успешные контакты — ценность продукта. Числа, сроки, принятые решения и чужие claims не выдумываются.
