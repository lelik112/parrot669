## Goal

Доказать или опровергнуть, что после явного назначения задачи в репозитории один выбранный агент начинает работу без ручного открытия его чата Алексеем.

## Problem

`docs/tasks/` служит памятью команды, но сейчас не посылает событий и не запускает агента. PM-042 описывает процесс; технический способ, разрешения и стоимость не установлены.

## Requirements

- Встроенные Automations в текущей среде доступны: плановые проверки возможны не чаще раза в час, GitHub webhook поддерживает события PR, но не изменения task Markdown. Проверить, может ли запускаться **конкретный существующий** агент, есть ли доступ к GitHub из запуска и доступна ли внешняя событийная/пятиминутная альтернатива. Если пробуждение чужих чатов недоступно, предложить честный fallback без имитации автономности.
- Проверить желаемый интервал около пяти минут или события; посчитать фактические лимиты/цену пустых проверок и полноценных запусков для пилота на одном агенте. Никаких фоновых запусков на всю команду до измерения.
- Выбрать безопасный формат назначения и проверку версии карточки перед claim; два параллельных события не должны дать два активных claim. Запись в репозитории не означает, что исполнитель прочёл задачу.
- Проверить на безвредной тестовой задаче путь: назначение → уведомление/пробуждение нужного агента → его подтверждённый claim → результат. Не трогать рабочие production/QA аккаунты и процессы PM-036/040.
- Перед реализацией общего механизма показать PM evidence, схему отказа/повтора, способ выключения и оценку расходов. Согласование доступа/инфраструктуры происходит отдельным решением владельца.

### Что сработало

[Пилот](logs/PM-043-pilot.md) (commit `5c20875d`) создал карточку `assigned` в GitHub; одноразовая задача ChatGPT была привязана к **текущему существующему** чату Игоря (scheduler вернул тот же conversation ID). В 2026-09-25 20:49:22 UTC run самостоятельно прочитал назначение, через GitHub connector записал `done` и ровно один `Claimed by: Игорь`. После выполнения одноразовая задача автоматически стала disabled; никаких постоянных проверок не работает. Это доказательство scheduled wake-up именно одного чата с GitHub read/write, но **не** доказательство события на Markdown-правку или 5-минутной рекурсии.

### Частота и способ запуска

- Публичная документация OpenAI о [scheduled tasks](https://learn.chatgpt.com/docs/automations) говорит, что задача внутри существующего чата может иметь **minute-based intervals** и сохраняет контекст. Однако доступный нам callable `automations.create` прямо ограничивает **любые recurring задачи интервалом не чаще 1 часа**. Его разрешённый одноразовый запуск и проверен. В Cloud Browser ChatGPT открыт без входа, поэтому UI настройку 5 минут на аккаунте Алексея проверить здесь не удалось. Это конфликт документации и конкретной доступной поверхности; 5-минутную возможность не обещаем.
- GitHub event trigger в этом ChatGPT connector поддерживает [активность pull request](https://learn.chatgpt.com/docs/automations#trigger-tasks-from-app-events); изменение `docs/tasks/*.md` на main событием для него не является. Даже отдельные репозитории агентов этого ограничения не снимают. Строить назначение через фиктивные PR только ради пробуждения не рекомендую.
- [Workspace Agents API](https://developers.openai.com/workspace-agents/trigger-runs) может запускать **опубликованного Workspace Agent** с API channel ID `agtch_...` и Workspace Agent access token. `conversation_key` продолжает разговор этого агента, `Idempotency-Key` дедуплицирует повтор триггера. Это иной тип агента; API не предоставляет проверенного вызова для произвольного существующего чата Игоря/Дениса/Марка. У нас не было опубликованного agent/channel/token для такого end-to-end теста; инфраструктуру и секреты не заводил. GitHub Actions по push/path мог бы отправлять такое событие **после отдельного решения** о published agent, но это будет другая сессия, не доказанное возобновление нынешних чатов.

### Версия и повтор

Формат минимального назначения: точный `Assignment ID`, `Assigned to`, `State: assigned`, scope/acceptance. Исполнитель перечитывает текущий GitHub blob SHA, проверяет точные строки состояния/адресата и отсутствие `Claimed by`; затем одной `github_update_file` пишет claim с прочитанным SHA. Один писатель выигрывает, другой получает 409, перечитывает и уходит при `claimed/done`. Если run не стартовал или GitHub недоступен, карточка остаётся `assigned`, claim не выдумывается; повтор безопасен после проверки версии. `blocked/done` не запускают работу, снятие блока требует нового назначения/ID. Выключение: pause/delete scheduled task; одноразовый пилот уже disabled.

Факт после пилота: повторное чтение `done` дало skip с одним `Claimed by`; попытка записи с **старым SHA** `b9027d8b...` вернула GitHub **409 CONFLICT**, версия `4722f141...` осталась целой. Локальная проверка точных состояний дала `assigned → claim_with_fresh_sha`, `done → already_claimed_skip`, `blocked → blocked_skip`, другой ID → `wrong_assignment`. Первое условие в пробном run обнаружило ложный substring match из-за текста протокола, было исправлено на точную строку **до записи**. Настоящие два одновременных пробуждения не запускались; атомарность SHA защищает именно один файл, не побочные эффекты, сделанные **до** claim.

### Нагрузка и стоимость

5 минут = **288 запусков/сутки** и **8 640 за 30 дней на агента**. Один час = 24/сутки, 720/30 дней. Для 4 агентов пять минут дали бы 34 560 полноценных запусков/30 дней; так делать до отдельного измерения не стоит. У callable Automations лимит 1 час; теоретические 5 минут ниже — только расчёт.

[Тариф ChatGPT Work/Codex](https://learn.chatgpt.com/docs/pricing): Standard GPT-6 Luna 2.5 credits/1M uncached input + 12.5/1M output; Sol 50 + 250. При **условных**, а не измеренных, 1 000 input и 100 output tokens на пустой check-in 8 640 запусков стоили бы ~32.4 credits Luna или ~648 credits Sol за 30 дней. При 10 000 input + 100 output: ~226.8 Luna или ~4 536 Sol. Cached tokens, tool outputs, reasoning и история длинного чата меняют итог; полная разработка после назначения стоит дополнительно. В инструменте пилота нет per-run tokens/credits, поэтому фактическая стоимость запуска **не измерена**. Цену credit в деньгах и quota аккаунта не выдумываем; их смотрит владелец в usage dashboard перед расширением.
