## Goal

Быстро и повторяемо обнаруживать поломки поиска доступного жилья и перехода к контакту, а также проверять безопасные web-регрессии после релизов. Результаты должны быть понятны Борису и Никите и привязаны к исходным задачам.

## Problem

Ручной регресс медленнее выпуска изменений; многократное открытие живого сайта в одном браузерном сеансе конфликтует с двумя аккаунтами QA. Нативный iPhone Safari недоступен, но это не должно останавливать обычные браузерные проверки.

## Context

Принято [D016](../decisions/D016-playwright-first-real-device-queue.md). В frontend сохранён `npm test` на `node --test tests/*.test.cjs`; после PR #54 Playwright подключён отдельным `npm run test:e2e` в CI с локальным fixture. После PR #57 четыре fixture-сценария проходят в трёх browser projects (PR CI 12/12); независимая QA и расширение покрытия ещё открыты. Реальный телефон и нативные проверки ведутся в [PM-041](PM-041-real-device-qa-queue.md). Текущие PM-036/029 ограничивают QA-аккаунты и сетевой доступ; автоматический запуск с состоянием авторизации не считать готовым без их проверки.

## Requirements

1. Денис до начала сверяет BUG-020, BUG-022, PM-036/029, существующий frontend CI и фактическую возможность тестов обращаться к согласованной среде. Фиксирует claim, Model check, узкий scope и границы с Игорем.
2. Подключить Playwright к frontend как отдельный воспроизводимый запуск, сохранив текущий `npm test`. Минимум: Chromium desktop и WebKit desktop; mobile viewport + touch emulation как отдельный явно подписанный проект. Firefox или дополнительные размеры только при найденном конкретном риске.
3. Первый smoke: публичный поиск по заранее известным тестовым данным → видимая карточка/даты → «Написать владельцу» → корректный объект и даты в гостевом черновике → auth gate без отправки. Отдельно короткие безопасные UI-сценарии Host/Messages (одна ссылка, возврат, языки, keyboard, отсутствие горизонтального переполнения на компактном viewport). Если стабильного fixture нет, сперва описать минимальный безопасный fixture/маршрут для запуска и отложить зависящие от него сценарии; не привязывать CI к случайным данным production.
4. После первого стабильного smoke составить матрицу **всех открытых задач** из [индекса](README.md): каждый обязательный критерий пометить `Playwright автоматизировано`, `browser manual`, `real-device PM-041` или `внешний ресурс` (контролируемый Airbnb, email). Приоритет автоматизации: P1 основной поиск/контакт/auth, затем повторяемые P2 UI/regression кабинета, календаря и сообщений. Для каждого доступного браузерного критерия либо добавить стабильный тест, либо оставить конкретную причину/manual step и owner; не закрывать всю матрицу первым PR искусственными skip.
5. Для двухаккаунтных сценариев, когда PM-036/029 позволяет доступ: изолированные browser contexts, отдельные согласованные тестовые аккаунты и данные, отсутствие общего state у параллельных тестов. Отдельная фаза после первого smoke: одно тестовое обращение → unread/ответ → read, привязанное к PM-003/BUG-020. Не отправлять реальные обращения владельцам и не менять реальные брони или Airbnb.
6. Запускать локально и в существующем CI только те тесты, которым доступна безопасная стабильная среда. Запись failed trace/screenshot достаточна для воспроизведения; сохранять артефакты ограниченное время и без секретов, cookies, личных сообщений/адресов. Не добавлять auth state в git; CI-ключи и права отдельно согласовать, если они потребуются. Нестабильный внешний backend не должен выдавать ложно-красный результат как баг UI.
7. Отчёт для каждого сценария: связанная task ID, Chromium/WebKit/emulated mobile, URL/fixture без секретов, PASS/FAIL/BLOCKED, ссылка на evidence и явно оставшиеся критерии real-device по PM-041. Никита может собирать короткий regression evidence; Борис решает критический acceptance по исходной карточке.

- [ ] QA независимо подтвердил, какие критерии PM-023/024/026/BUG-019/020/PM-020 покрыты автоматическим web evidence, а какие остаются ручными или real-device в PM-041.
