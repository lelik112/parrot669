# PM-008 — Пилот и измерение результата MVP

**Title:** подготовить небольшой пилот и учёт реального поиска/контакта.

**Status:** planned — discovery. **Priority:** P1. **Owner:** Марк / PM, постановка; запуск не начат.

**Agent:** Марк / Product Manager. **Recommended model:** Luna. **Recommended reasoning:** Medium. **Reason:** текущий этап — ограниченный discovery и определение измеримых гипотез MVP; исходные показатели и пилотная группа пока неизвестны, поэтому факты нельзя заполнять догадками.

**Model check:** применяется перед возобновлением работы над планом; запуск пилота требует отдельного решения владельца.

**Area:** продукт / исследование. **Updated:** 2026-09-24.

## Goal

Получить основания для следующего продуктового решения: владельцы добавляют полезное предложение, гости находят жильё, между ними происходит контакт.

## Problem

Большое число реализованных возможностей не показывает, нужен ли сервис. В прочитанных документах нет выбранной группы пилота, исходных показателей или числовых целей.

## Context

Поиск технически уже поддерживает разные страны/города; это не равно решению продвигаться сразу везде. Объект может находиться без внешней ссылки и при выключенных сообщениях. Нужно отделять полезную выдачу от карточки, по которой нельзя сделать следующий шаг.

## User

Первые владельцы и гости; владелец продукта, выбирающий, что развивать дальше.

## Value

Решения о приоритетах по реальным затруднениям и результатам, а не по количеству фич.

## Solution

Выбрать с владельцем один ограниченный сегмент/канал/географию пилота и вести минимальный учёт наблюдений. Сначала использовать доступные данные и ручную запись результатов; отдельная аналитическая система не является обязательной частью этой задачи.

## Requirements

- Уточнить первую группу, канал привлечения и доступные реальные показатели. Не придумывать участников, размер выборки, дату запуска и цели.
- Описать короткий сценарий владельца и гостя; проверять причины отказа/неудачи, а не только успехи.
- Заранее определить период наблюдения, единицы и знаменатели показателей. Исключить QA-аккаунты/объекты и не считать отсутствие данных нулём.
- Отдельно учитывать доступность пути связи: внутренние сообщения либо опубликованный внешний переход. Переход на внешнюю площадку — только proxy-показатель, не доказанный контакт.
- Собрать наблюдения о понимании доступности/цен и календарной проверки; не публиковать персональные данные участников.

## Предлагаемые показатели

| Гипотеза | Определение |
| --- | --- |
| Владельцы добавляют жильё | Приглашённые владельцы, создавшие объект с будущей доступностью / приглашённые в определённой группе |
| Гость получает полезную выдачу | Поиски хотя бы с одним подходящим результатом и доступным путём связи / наблюдаемые поиски |
| Начинается контакт | Поиски, после которых отправлено первое сообщение / наблюдаемые поиски; внешние клики отдельно |
| Владелец участвует | Обращения с ответом в выбранном окне / обращения, для которых окно уже прошло; время до ответа |
| Доступность достоверна | Сообщённые расхождения между показанными и фактическими условиями, с контекстом и источником |
| Проверка понятна | Завершённые задания / начатые; причины неудачи, выхода или обращения за помощью |

Это определения для согласования, не утверждение о наличии телеметрии. Анонимную цепочку поиск → сообщение нельзя считать измеряемой, пока способ сопоставления не выбран.

## Acceptance criteria

- [ ] В задаче записаны конкретный сегмент/канал, участники или способ набора, окно наблюдения и доступ к данным.
- [ ] Есть исходные числа либо точный перечень отсутствующих данных; цели определены владельцем и PM с основанием.
- [ ] Отдельно записаны случаи «объект найден, пути связи нет» и предложение простого исправления; автоматическое включение сообщений не считается выбранным решением.
- [ ] После пилота есть факты и вывод по трём гипотезам MVP с ограничениями выборки, а также обоснованное следующее действие.

## Alternatives

Продолжать расширять функциональность без пилота; сразу строить большой аналитический стек; начать с небольшого ручного наблюдения. PM рекомендует последний вариант до появления подтверждённой потребности в автоматизации.

## Rejected

Выдуманные показатели, бронирования как метрика несуществующей функции, объявление каждого внешнего клика состоявшимся контактом, включение приёма сообщений без согласия владельца.

## Success criteria

Результат пилота позволяет объяснить, где участники получают ценность или застревают, и выбрать следующую задачу. Успешная настройка счётчиков сама по себе не является успехом продукта.

## Not doing

Массовое привлечение во все города, рассылки от имени владельца без поручения, новая аналитическая инфраструктура, гарантии результата на неизвестном размере выборки.

## Dependencies

Ответ владельца о первой группе и имеющихся данных; рабочий контакт PM-003. Планирование можно вести до завершения QA; результаты пилота не объявлять заранее. Предложения Алекса используются с атрибуцией, если переданы владельцем.

## Evidence

Исходные метрики и результаты пилота не предоставлены. Числовых выводов пока нет.
