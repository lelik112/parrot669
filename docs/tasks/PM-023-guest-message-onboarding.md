# PM-023 — Путь гостя к первому сообщению

**Title:** убрать ранний auth-wall при переходе из поиска к обращению владельцу.
**Status:** assigned to Игорь / Developer — claim и Model check ещё не записаны в main; начало реализации не подтверждено. **Priority:** P1.
**Owner:** Игорь / Developer (назначен Алексеем); QA Борис.
**Agent:** Игорь. **Role:** Developer. **Scope:** frontend UX Messages и продолжение после входа/регистрации; серверные правила доступа остаются обязательными.
**Recommended model:** Sol. **Recommended reasoning:** Medium. **Reason:** сценарий связывает поиск, черновик сообщения, регистрацию/подтверждение email и возврат пользователя; важно не потерять контекст и не открыть приватные диалоги.

## Goal

Гость с конкретным намерением написать владельцу понимает, зачем нужна учётная запись, может подготовить обращение и после входа или регистрации продолжить именно этот сценарий.

## Problem

На мобильном переход в **Messages** без сессии сразу показывает вход/регистрацию. Гость может не понимать, зачем аккаунт нужен и что будет после регистрации. Это создаёт лишнее препятствие на основном пути «нашёл жильё → связался с владельцем».

## User

Гость без аккаунта, который нажал «Написать владельцу» в результатах поиска; также пользователь, открывший Messages без выбранного объекта.

## Value

Понятный переход от найденного жилья к первому обращению без потери выбранного объекта, дат и введённого текста; приватность существующих диалогов сохраняется.

## Solution

Предлагаемый flow для первого обращения: из карточки жилья гость попадает в контекст нового сообщения, может набрать текст и даты, а вход/регистрация требуются при отправке. После входа либо создания аккаунта и подтверждения email PARROT возвращает его к тому же объекту и черновику. Если пользователь открывает Messages без конкретного жилья, объяснить, что аккаунт нужен для приватных диалогов, и дать понятные действия «Войти» / «Создать аккаунт».

## Requirements

- Сохранять кнопку **«Написать владельцу»** для каждого объекта, оставленного в поиске, независимо от старого host-wide opt-in; сохранять контекст объекта и найденных дат (D011/PM-024).
- Для гостя без сессии показать форму нового обращения и ясно сообщить, что аккаунт требуется для отправки и хранения переписки.
- Не отправлять сообщение до успешной аутентификации и выполнения действующих правил подтверждения email.
- Сохранять текст и даты при переключении между входом и регистрацией, после подтверждения email и при возврате в Messages; не смешивать черновики разных аккаунтов.
- Не показывать до входа список, историю или содержимое чужих/собственных существующих диалогов.
- Для прямого открытия Messages без объекта сохранить вход/регистрацию для доступа к приватному inbox, но объяснить назначение экрана и путь начать обращение из поиска.
- Проверить сценарии на мобильном и desktop; поддержать RU/EN/ES/CA.
- Не менять слоган страницы For Host в рамках этой задачи.

## Acceptance criteria

- [ ] Гость из поиска может подготовить текст обращения и даты до регистрации/входа.
- [ ] При отправке гость получает ясное предложение войти или создать аккаунт; после завершения auth возвращается к тому же объекту, датам и черновику.
- [ ] До auth никакое сообщение не отправляется и никакая история диалогов не раскрывается.
- [ ] Старый host-wide opt-in не скрывает кнопку и не блокирует первое обращение по объекту, который оставлен в поиске; старые диалоги доступны после входа.
- [ ] Прямой вход в Messages без контекста объясняет требование аккаунта и не выглядит ошибкой или пустым тупиком.
- [ ] Работают вход существующего пользователя, регистрация нового, подтверждение email и восстановление после перезагрузки в пределах предусмотренного срока черновика.
- [ ] Объект, выбранные даты и черновик не теряются при переходах; состояния разных аккаунтов изолированы.
- [ ] Все основные тексты и состояния согласованы на RU/EN/ES/CA и проверены на мобильном и desktop.
- [ ] Борис подтверждает основной путь «поиск → черновик → auth → отправка» отдельными аккаунтами; PM-003 остаётся отдельной проверкой полного обмена сообщениями.

## Alternatives

- Требовать вход сразу при переходе в Messages — проще, но не даёт гостю начать обращение и слабо связывает регистрацию с намерением написать.
- Разрешить отправку анонимно — убирает регистрацию, но ломает приватную историю и требует отдельной модели контакта.

## Rejected

Анонимная отправка; показ inbox или истории до входа; потеря черновика при регистрации/подтверждении email; изменение формы объявления For Host в этой задаче.

## Success criteria

Успешно пройти проверенный сценарий от кнопки в поиске до первого отправленного сообщения после auth. В аналитике пилота отдельно считать переходы: кнопка контакта → начало черновика → auth start/completion → отправка. Числовой порог установить после получения базового уровня.

## Not doing

Редизайн слогана For Host, изменение регистрации для владельцев, новые способы входа, изменение правил email verification, анонимная переписка, перестройка backend сообщений или полного inbox.

## Dependencies

[D009](../decisions/D009-host-cabinet-ia.md) и PM-020 задаёт навигацию и вход в Messages. Перед разработкой сверить обновления PM-020, действующий auth contract и draft behavior. PM-003 остаётся независимой QA-приёмкой основного контакта; PM-006 покрывает email-сценарии.

## Evidence

В текущем frontend выдача добавляет «Написать владельцу» только при `acceptingNewConversations`; это известное расхождение с D011, которое устраняет PM-024. Ссылка ведёт в `/messages.html` с ID объекта и, при наличии, датами. В `public/assets/messages.js` для неавторизованного пользователя приложение скрывает inbox и показывает auth-блок. Основной сценарий двух участников и QA evidence ведутся отдельно в [PM-003](PM-003-contact-acceptance.md).
