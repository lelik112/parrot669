# PM-037 — безопасная длина публичного поиска по датам

**Title:** определить и ограничить число ночей в одном публичном запросе поиска.

**Status:** planned / NEXT. **Priority:** P2; повысить только при замере ухудшения или доступного воспроизводимого отказа. **Owner:** Марк / Product Manager — предложение продуктового предела; **suggested developer:** Игорь / Developer, без claim. **Origin:** [PM-034-BE](PM-034-BE-backend-audit.md), [backend report](logs/PM-034-backend.md).

**Agent:** Марк. **Role:** Product Manager. **Scope:** контракт и критерии; реализацию и замеры проводит назначенный разработчик.

**Recommended model:** Sol. **Recommended reasoning:** High. **Reason:** публичный endpoint, ночные диапазоны, SQL `generate_series`, совместимость поиска, даты checkout-exclusive и риск нагрузки. **Model check:** до основной работы.

## Goal

Публичный запрос с чрезмерно длинным диапазоном не заставляет базу выполнять несоразмерную работу и не скрывает от гостя, почему поиск невозможен.

## Problem / Context

В текущем backend `SearchService.search` проверяет `to > from`, но верхней границы числа ночей нет. `SearchRepository` обрабатывает запрошенные ночи через `generate_series` и кандидатов. Игорь подтвердил путь по коду; нагрузка и допустимая продуктовая длина проживания **не измерены и не утверждены**. PARROT не определяет юридический срок аренды и не должен заявлять пользователю, что более длинное проживание запрещено.

## Requirements

- PM + разработчик формулируют **предложение предела для одного поискового запроса**, обосновав выбор реальными ожидаемыми stay-сценариями, стоимостью SQL и доступными замерами на изолированных данных. Число ночей до этого не считать принятым.
- До реализации принять это число как UX/API контракт; error copy объясняет ограничение именно запроса PARROT, а не допустимый срок аренды. Уточнить поведение UI на EN/ES/CA/RU и сохранённой форме.
- Backend отвергает запрос за пределом до основного SQL понятным 400; проверяются точная граница, превышение, нулевой/отрицательный интервал, слишком далёкие даты и overflow вычисления. Checkout остаётся исключающей датой.
- При необходимости добавить UI валидацию с тем же пределом и текстом; серверная защита обязательна независимо от UI.
- Изолированный тест/EXPLAIN на реалистичном объёме подтверждает, что допустимый интервал работает, а отвергнутый не запускает тяжёлый поиск; production не использовать для нагрузочного эксперимента.

## Acceptance criteria

- [ ] Утверждено число ночей и основание выбора; оно указано в задаче до кодового claim на реализацию.
- [ ] При допустимой границе выдача и цены совпадают с прежними; при превышении сервер возвращает 400 с понятным UI-сообщением, основной SQL не исполняется.
- [ ] Поиск по короткому интервалу, смена даты, сохранённые фильтры, выбранные даты в пути до сообщения и PM-001 semantics не меняются.
- [ ] Есть тесты границ и итоговая независимая QA, с отдельной проверкой обычного пользовательского поиска.

## Not doing

Глобальное ограничение длительности аренды, переписывание SQL поиска, введение бронирований или нагрузочное тестирование production.

## Dependencies
