## Goal

Новый Regression QA после первоначального безопасного доступа самостоятельно выполняет гость A → сообщение хозяину B → ответ B → проверка ответа A, refresh/logout обоих сеансов и UI/regression ретесты, не переключая аккаунты Алексея и не трогая текущую пару/задания Бориса.

## Problem

[D013](../decisions/D013-qa-acceptance-regression-split.md) вводит отдельного Regression QA — Никиту; доступ к двум независимым браузерным сессиям и тестовым участникам для него пока не подтверждён. [PM-029](PM-029-two-origin-qa-sessions.md) даёт Борису два origin и backend allowlist **только** для account ID существующих `qa`/`lelik`. Одновременная работа двух QA под одной парой может смешать сообщения, блокировки, unread, logout и evidence. Кроме того, PM-016/003 сейчас открыты после block-теста и потери видимого `lelik`-сеанса; использовать эту пару новому QA нельзя.

## User / Value

Новый Regression QA Engineer — независимая двухаккаунтная проверка без вмешательства в критический acceptance Бориса. Команда получает более быстрый feedback по исправлениям Messages/кабинета без ложных PASS от пересекающихся тестовых данных.

## Solution / порядок выбора

1. Сначала подтвердить реальную среду нового агента: сколько браузерных контекстов/профилей он **может самостоятельно контролировать** и сохраняются ли отдельные cookie между действиями. Имя Никита известно со слов владельца; browser API, два одновременно доступных входа и отдельная тестовая пара ещё не подтверждены его QA-отчётом.
2. Выделить **два отдельных обычных подтверждённых тестовых аккаунта** и безопасный тестовый объект/диалог новому QA с владельцем тестового объекта; их stable account IDs фиксируются только в защищённой настройке allowlist при её необходимости. Пароли, cookies, IDs с привязкой к секретам и токены не записывать в публичные docs.
3. Если у нового QA реально есть два независимых browser contexts на основном origin, проверить этот вариант первым: backend/Worker guard PM-029 не менять.
4. Если доступен только один browser context, проверить существующую схему двух origin PM-029. Для **новой пары** QA origin сейчас закрыт backend allowlist. Перед расширением разработчик описывает точное изменение, его границы, provisioning/отзыв отдельных QA account IDs и negative tests; Марк фиксирует решение о точном перечне разрешённых ID с Алексеем до выпуска. Сохранять исходный `qa`/`lelik` доступ для Бориса и fail-closed Worker attestation; не делать общую привилегию «любой QA», username-based allowlist или публичный QA mode.
5. В любом выбранном варианте задокументировать кто владеет парой, как безопасно войти в первый раз и восстановить вход без раскрытия credentials, как остановить тест и отозвать доступ после смены QA. Не зависеть от ручного переключения Алексеем между сообщением и ответом.

## Requirements

- Сверить свежие [PM-029](PM-029-two-origin-qa-sessions.md), [PM-016](PM-016-qa-second-session-access.md), [BUG-021](BUG-021-blocking-signs-out-host.md) и [D013](../decisions/D013-qa-acceptance-regression-split.md), текущие claims и реальные доступные новому QA браузерные инструменты. Не ломать восстановление пары Бориса и его pending security checks.
- Развести аккаунты и тестовые данные двух QA: каждый имеет свой диалог/объект, чтение/блокировки/уведомления одного не изменяют тестовый прогон другого. Не утверждать полной изоляции пользовательских данных, если общий backend её не обеспечивает; обычные authorization rules остаются.
- Для второго origin backend по-прежнему проверяет стабильные IDs, подтверждённую аутентификацию и серверную Worker attestation на **всех** QA API. Отсутствующая/неверная attestation, чужой confirmed account, анонимный запрос к данным и поддельные клиентские `Origin`/`Host`/заголовок не дают доступ.
- Обычный `parrot669.com` сохраняет обычные права и поведение; QA access не превращается в impersonation, master-password или shortcut мимо email verification/CSRF.
- Обе вкладки остаются на своих origin при Search → Messages → Host, после refresh; logout A не разлогинивает B, logout одного QA не меняет рабочие сеансы другого.
- При необходимости изменять backend/Worker/настройку только в отдельном явно заявленном developer scope, с CI/security checks, deployment evidence и independent QA; не смешивать с PM-029 security QA или PM-034 audit branch без согласования.

## Acceptance criteria

- [ ] У нового QA есть собственная подтверждённая пара тестовых аккаунтов и два самостоятельно управляемых сеанса; имя исполнителя/среда/способ первоначального безопасного входа записаны без секретов.
- [ ] В его **собственном** browser API одновременно видны A и B: сообщение A → ответ B → ответ A; refresh обоих, logout/login A и B независимы. Проверка проводится на безопасном тестовом объекте, с восстановлением исходного состояния при необходимости.
- [ ] Борис во время и после отдельного прогона сохраняет свою пару/данные/доступ по PM-029 и может продолжать собственный acceptance; negative checks PM-029 не объявляются выполненными этой задачей.
- [ ] Если расширен QA allowlist: новая пара разрешена только по stable account ID; посторонний подтверждённый аккаунт, аноним, forged headers и неверная Worker attestation отклоняются в backend; обычный origin не получает новых привилегий. Результаты CI, деплой и независимый live ретест указаны без токенов.
- [ ] Если backend менять не понадобилось: записано, какими двумя независимыми browser contexts это достигнуто, почему PM-029 guard остался неизменным и какие проверки уже реально прошли.
- [ ] Есть документированный безопасный отзыв QA-доступа и границы доступа к тестовым данным. Smoke нового QA оформлен как regression evidence; финальный critical acceptance Бориса не присваивается автоматически.

## Alternatives

- Одна общая пара `qa`/`lelik` для Бориса и нового QA с координацией по времени: технически проще, но создаёт столкновения тестов и повторяет нынешнюю проблему block/unread. Использовать только как временную явно согласованную проверку, не как целевое решение.
- Только односторонний smoke под одним аккаунтом: полезен для UI, но не разблокирует двухстороннюю Messages regression.
- Второй независимый browser profile/context на основном origin: предпочтителен, если доступен новому агенту; не требует расширять QA origin.

**Отзыв:** для QA origin удалить только две строки по подтверждённым immutable IDs; [guard](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/src/main/scala/com/parrot669/http/QaOriginGuard.scala#L64-L70) перестанет пропускать даже уже открытую сессию на следующем API вызове. Обычный доступ на основном origin живёт по стандартным правилам: если надо закрыть и его, отдельно завершить сессии/заблокировать тестовые аккаунты по согласованной процедуре. Сами QA-объекты и сообщения остаются в общей БД; отдельные аккаунты исключают пересечение обычной приватной переписки, но не обещают скрыть опубликованное жильё из общего поиска.

**Проверка после provisioning:** уже есть [backend CI smoke](https://github.com/lelik112/parrot669-backend/blob/3e35c4681bc46a65f067c53fef1f30ad8f197856/scripts/smoke-test.sh#L298-L337) для allowed/third/anonymous, регистраций на QA origin и неверного секрета. Если нет прямого управляемого доступа к БД, это инфраструктурная зависимость, а не повод добавлять публичный admin endpoint.

**Blocker:** новый Regression QA не назван и не имеет известного browser API, отдельные подтверждённые аккаунты/объект не выделены; точные IDs для дополнительного допуска владельцем не согласованы. Tabs on the same hostname share its `parrot_session` cookie; a new login on that hostname replaces the browser's previous cookie while the backend retains the earlier session. Prepared two dedicated Workers (`parrot669-regression-a` and `parrot669-regression-b`) on the same account's workers.dev subdomain. Both use the existing QA secret attestation and the backend's immutable-ID allowlist; both fail closed when their `QA_WORKER_SECRET` binding is absent. Backend code/session policy stays unchanged. QA-specific data are ordinary account-scoped messages, not a separate database.
