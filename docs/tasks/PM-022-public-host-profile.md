# PM-022 — Публичный профиль хозяина

**Title:** согласовать гостевой просмотр хозяина из объекта без раскрытия закрытых данных.
**Status:** planned — продуктовый контракт готов к решению владельца; реализация LATER после первой QA-волны. **Priority:** P2. **Owner:** исполнитель не назначен.
**Agent:** будущий Developer после продуктового решения; **Role:** Developer. **Scope:** согласованный гостевой UI/публичные ответы и QA приватности.
**Recommended model:** Sol. **Recommended reasoning:** High. **Reason:** публичная поверхность пересекается с существующим public-profile JSON, PM-002 и контролем доступа к contact/calendar данным.
**Model check:** до claim исполнитель сверяет конкретный публичный контракт и текущие endpoints; при недостаточной мощности действует D005.

## Goal
Гость понимает, кто разместил объект и как с ним связаться разрешённым способом, без неподтверждённых обещаний доверия.

## Problem
Backend уже отдаёт ограниченный публичный профиль, но его страница/путь из результатов поиска и допустимые поля не согласованы. Алекс предложил карточку с фото, About и соцсетями; сейчас публикация этих данных и ссылки Airbnb зависит от отдельных решений.

## User
Гость, рассматривающий доступный объект; владелец, управляющий раскрытием своих данных.

## Value
Прозрачное происхождение объявления и доступный путь контакта с хозяином в рамках согласия владельца.

## Solution
Сначала определить минимальные поля и точку входа из объекта, сверить текущий public-profile JSON и политику публикации; реализовать только после принятого контракта. При отсутствии разрешённой информации показать уже существующие факты об объекте/контакте без выдуманной репутации.

## Requirements
- Проверить фактические публичные поля/backend и связь «поиск → объект → хозяин»; не утверждать, что API-профиль уже равен готовой странице.
- Таблица видимости: display name, объект, ссылка Airbnb, конкретный статус calendar verification, last synced, контакт через PARROT, будущие About/фото/внешние ссылки. Для каждого поля указать источник, разрешение и состояния пусто/снято/устарело.
- Никаких необъявленных личных email, точных адресов и координат, приватного iCal URL, сообщений, периодов владельца и необязательных внешних контактов в публичных ответах/странице.
- Значок проверки отражает только конкретный подтверждённый факт и актуальность PM-001; не обещает личность/законное право сдачи жилья. Нельзя называть legacy v1 подтверждением выбранных дат.
- Показ внешней ссылки согласовать с принятым D010/PM-002 сразу для поиска и профиля; не создавать второй обход неопределённого правила.
- Отсутствие опубликованной ссылки/профиля не исключает подходящий объект из поиска; для объекта в поиске доступен PARROT-contact path по D011 независимо от прежнего host-wide opt-in.

## Acceptance criteria
- [ ] Принята таблица публичных полей и состояний, определён переход из объекта; PM-002 решает внешний линк, PM-021 — новые личные поля.
- [ ] Существующие публичные ответы и новый гостевой экран следуют одной privacy/visibility модели.
- [ ] QA проверил владельца с данными/без них, контакт по D011, неподтверждённый/старый календарь и отсутствие утечки секретов; публичные поля всё равно ограничены отдельным consent contract.
- [ ] Страница не показывает общий статус «надёжный хозяин» и не мешает поиску объекта без Airbnb.

## Alternatives
Сохранить только имя на карточке и кнопку «Написать»; отдельная ограниченная публичная страница; расширенная карточка после пилота.

## Rejected
Обязательный профиль ради допуска в поиск, автоматическая публикация новых контактов и Instagram, собственный рейтинг на пустой истории.

## Success criteria
Гость понимает источник сведений и может воспользоваться разрешённым контактом; проверяем это в пилоте PM-008, не считаем просмотр страницы фактом контакта.

## Not doing
Instagram verification, фото Airbnb, публикация контактов без отдельного разрешения, новый рейтинг, booking/payment.

## Dependencies
PM-019; согласованные поля/согласие PM-021; принятое D010/PM-002 о внешней ссылке; независимая QA PM-001 по сигналу календаря. PM-021 уже слита в оба main, но остаётся in review; согласие на новые публичные поля отдельно. Первая QA-волна PM-030 предшествует запуску новой разработки. Отдельный release только после принятия этих границ.

## Evidence
Backend public-profile JSON уже существует с ограниченным доступом; самостоятельная гостевая страница и новые поля не приняты.

## Product contract proposal — PM-030, 2026-09-25

**Статус:** предложение Марка для решения Алексея; реализация и новые публичные поля не утверждены. Рекомендуемый минимальный выпуск — отдельная гостевая страница из карточки **выбранного** объекта. Она показывает уже доступное гостю имя хозяина и контекст этого объекта, сохраняет видимое действие «Написать владельцу». Переход к профилю не становится условием контакта. PM-027/028 открывают владельцу приватные разделы из Messages и не являются гостевым профилем.

В текущем backend `GET /api/p/{parrotId}` уже публично возвращает `profile.parrotId/displayName/createdAt`, **все** объекты профиля с ограниченными фактами, опубликованные валидные Airbnb listings с `calendarControlStatus`, а также отдельный массив `verifications[]`. Это существующий API, а не согласие на показ всей коллекции на новой странице. Email, точный адрес/координаты, сырая iCal-ссылка и сообщения в DTO не входят. Запись `verifications[]` нельзя автоматически превращать в D002 calendar-control badge: там могут быть legacy-записи. Источники сверены с `ProfileRoutes`, `ProfileService`, `Models`, `PublicLinks` в backend main.

| Сведения | Источник и предлагаемая гостевая видимость | Нет данных / снято / устарело |
| --- | --- | --- |
| Имя хозяина и PARROT ID | `profile.displayName` и `parrotId`, уже публичны в API; на новой странице показывать после понятного уведомления владельца о публичности имени в PM-021 | Нет корректного имени → нейтральный идентификатор, без «проверен»; смена имени обновляет публичный показ |
| Выбранный объект | Только название, город, тип/вместимость и id объекта, из которого открыт профиль; не перечислять остальные объекты автоматически | Объект больше не доступен через публичный путь → не показывать устаревший guest CTA/внутренние данные; определить безопасное пустое состояние |
| Airbnb-ссылка | Только валидный URL, который владелец разрешил публиковать, по D010; переход не зависит от календарной проверки | Нет/скрыта/невалидна → нет ссылки, нейтральный текст; объект и PARROT-контакт остаются |
| Контроль календаря | Только текущий `calendarControlStatus` для соответствующего источника по D002/D010; `verified` описывает контроль источника, не личность/право сдавать | `unverified/pending/recheck_required`, отсутствие ссылки и legacy v1 → нет verified-бейджа; текст состояния из PM-031 |
| Last synced | Не показывать в минимальной версии: дата синхронизации не содержится в public-profile DTO и сама по себе не гарантирует актуальность жилья | Вопрос о публичном источнике, времени и устаревании решать отдельным контрактом |
| Контакт | PARROT Messages для объекта, если он выдаётся в поиске, по D011; вход/подтверждённая почта перед отправкой, без скрытой отправки | При блокировке пары действует текущее правило; email/телефон не раскрывать |
| About, фото, Instagram, внешние контакты | Не хранятся в PM-021 и не выпускаются в этом минимальном объёме | Для каждого нового поля позже отдельное явное согласие, управление публикацией и снятием |
| Личные и внутренние данные | Email, точный адрес, координаты, iCal URL, сообщения, частные периоды и список всех объектов не размещать на странице | Backend public JSON отдельно проверить на соответствие принятому объёму до релиза |

**Предложение на approval Алексею:** принять минимальный вариант «имя хозяина + выбранный объект + существующие фактические сигналы + контакт», с уведомлением о публичном имени; весь портфель объектов, новые биографические поля и last synced отложить. Если отдельная страница без новой информации не помогает гостю выбрать и написать, оставить имя на карточке и кнопку контакта до данных пилота PM-008.

**Открытые решения перед dev claim:**

1. Нужна ли отдельная публичная страница с этими минимальными данными уже сейчас, или достаточно карточки поиска и контакта до пилота? Рекомендация PM: после QA первого контакта и при наличии подтверждённой потребности.
2. Принимается ли показ только выбранного объекта на странице, при том что существующий API уже отдаёт полный список и legacy `verifications[]`? Рекомендация PM: не выводить портфель и не делать из legacy-записей trust badge; разработчик сверит/API ограничит экспозицию по принятому контракту.
3. Уведомление хозяина о публичном имени в приватном профиле и безопасное поведение для старого/удалённого объекта должны быть конкретизированы при запуске разработки.

**Ready for approval** относится только к продуктовому контракту. PM-022 не передаётся разработчику, пока Алексей не примет объём, а первая QA-волна PM-030 не покажет, что путь поиска и контакта стабилен.
