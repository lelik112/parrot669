# PM-034 — Backend and Frontend Refactoring Audit

**Title:** аудит технического долга backend и frontend без запуска переписывания.

**Status:** planned. **Priority:** P2. **Owner:** Марк / Product Manager.

**Agent:** Марк. **Role:** Product Manager. **Scope:** постановка задачи, координация, документация; без кода и технических изменений.

**Audit executors (not claimed):**
- Игорь — backend audit.
- Денис — frontend audit.

Указание исполнителя не означает автоматический claim или начало работы.

**Recommended model:** Sol. **Recommended reasoning:** High.

## Goal

Определить, где накопленный технический долг PARROT 669 реально мешает развитию и какие изменения имеют смысл до дальнейшего масштабирования.

## Requirements

Backend audit:
- структура модулей;
- Routes/Main;
- service/repository boundaries;
- доменные границы;
- дублирование;
- тестируемость;
- сложность добавления новых фич;
- кандидаты на выделение модулей.

Frontend audit:
- структура страниц;
- JS-модули;
- повторение логики;
- API/auth слой;
- состояние форм;
- i18n;
- переиспользование UI;
- готовность к profile, public host profile, FAQ и trust signals.

## Result format

# REFACTOR AUDIT

## NOW

Проблема, влияние, размер S/M/L, риск Low/Medium/High, рекомендация.

## NEXT

Что желательно сделать в ближайших этапах с той же оценкой.

## LATER

Что можно оставить без изменений и почему.

## DO NOT TOUCH

Что не нужно рефакторить и почему.

## Critical rules

Не предлагать рефакторинг только потому, что код выглядит некрасиво.

Рекомендация должна быть связана с:
- препятствием выпуска фич;
- ростом риска багов;
- усложнением тестирования;
- дублированием бизнес-логики;
- рисками роста нагрузки или команды.

Не превращать аудит в rewrite проекта.

## Not doing

- код;
- PR приложения;
- миграции;
- архитектурные изменения во время аудита;
- большой rewrite.
