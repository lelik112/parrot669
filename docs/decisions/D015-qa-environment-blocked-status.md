# D015 — QA blocked, если нет обязательной среды

**Status:** accepted. **Agent:** Марк. **Role:** Product Manager. **Related tasks:** [PM-030](../tasks/PM-030-qa-drain-next-stage.md), [PM-039](../tasks/PM-039-browser-test-environments.md).

Decision:
Задача переходит в `blocked`, если реализация готова, доступных независимых проверок по её обязательным критериям больше не осталось, а закрытие зависит от недоступного устройства, браузера или профиля. В карточке указываются конкретный ресурс, условие разблокировки, ранее полученный частичный PASS и ответственный за следующий шаг. Если остались доступные desktop/web проверки, задача остаётся `in review` с явной пометкой `mobile/native blocked by PM-015/014` для соответствующих критериев. `blocked` не означает дефект приложения и не отменяет уже проведённый QA.

Problem:
Десятки задач с меткой `in review` выглядели как ожидающие обычного прогона Бориса, хотя у него нет управляемого телефона и нативного Safari с сохранённым адресом. Очередь не показывала реальную зависимость и искажала планирование.

Reason:
Один статус должен подсказывать исполнимое следующее действие. Разделение общего статуса и блокировки отдельного критерия сохраняет доступную QA-работу и честно отражает, что desktop/emulation и owner-assisted скриншот не подтверждают независимый real-device сценарий.

Alternatives:
Держать все задачи в `in review` до появления телефона; закрывать их по desktop/emulation; блокировать все задачи, где хотя бы раз упомянут mobile, даже если осталось много desktop QA.

Rejected:
Автоматическое закрытие mobile критериев по изменению CSS, зелёному CI, desktop viewport или телефону владельца без управляемого независимого прогона; глобальная остановка доступной desktop QA.

Date:
2026-09-25; поручение Алексея сделать статус честным после отчётов Бориса. Пилот выбора инструмента ведётся Марком в PM-039. Снятие блокеров происходит только после фактического доступа и evidence QA.
