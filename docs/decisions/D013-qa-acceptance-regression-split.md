# D013 — разделение Acceptance QA и Regression QA

**Decision:** добавить роль Regression QA Engineer как отдельную полосу smoke, регрессии и повторной проверки исправлений. Борис остаётся QA Lead / Acceptance QA и отвечает за итоговую независимую приёмку критических пользовательских сценариев. Имя нового агента и доступы ещё не определены; роль не означает активный claim.

**Problem:** разработка опережает независимую проверку, а очередь `in review` смешивает сложный acceptance и повторяемые UI/regression ретесты. Единственный QA стал узким местом обратной связи.

**Reason:** параллельная подготовка воспроизводимого evidence и коротких ретестов освобождает Бориса для вопросов, где нужно проверить ценность и продуктовые границы: найти доступное жильё, связаться с владельцем, получить ответ, подтвердить корректность календаря и безопасность аккаунтов. Новый QA ускоряет feedback loop, не создавая второго конкурирующего владельца одного acceptance.

**Alternatives:** оставить все QA-задачи Борису; передать новому человеку половину задач без разделения характера проверки; автоматизировать весь регресс прежде чем открыть новый QA слот. Для части повторяемых проверок автоматизация позже полезна, но не заменит независимый осмотр UI и evidence сейчас.

**Rejected:** объявить второго QA равноправным владельцем финальной приёмки всех задач; переносить критический acceptance или приватность/безопасность по умолчанию; считать назначение роли подтверждением, что новый агент подключён или имеет браузер/аккаунты/устройство; закрывать задачу по одной записи smoke, если её acceptance criteria шире.

**Date:** 2026-09-25.

**Source:** прямое поручение Алексея через предложение Алекса добавить второго QA и явно разделить его роль с Борисом. Авторство стратегического предложения — Алекс; решение принять изменение команды — Алексей.

## Операционный контракт

- **Борис — QA Lead / Acceptance QA:** определяет полноту evidence и сообщает итоговый результат по критическим путям (поиск → сообщение → ответ, источник доступности/календарь, авторизация/изоляция/приватность, спорные сценарии), оценивает баги совместно с PM. Его `PASS` не заменяется smoke второго QA.
- **Regression QA Engineer — новый участник, имя TBD:** проверяет стандартные сценарии, исправления, UI/UX, локализацию, smoke релиза; записывает шаги, окружение, ожидаемый/фактический результат и evidence, отмечает блокеры. Может выполнить **полную** приёмку только отдельным явным назначением в карточке с критериями и необходимой средой; тогда не нужна дублирующая подпись Бориса, если критический сценарий этому назначению не противоречит.
- **Марк / PM:** разводит очередь и не назначает один и тот же ретест одновременно двум людям; владелец конкретной карточки и её acceptance criteria остаются явными. Отчёт второго QA может быть частью общего acceptance, но сам по себе не меняет `in review` → `done`.
- Старт любого QA: конкретная карточка, `Agent / Role / Scope`, claim, model check, безопасная среда и доказательства. Роль не создаёт доступ к браузеру, тестовому аккаунту, Safari, почте или календарю.
