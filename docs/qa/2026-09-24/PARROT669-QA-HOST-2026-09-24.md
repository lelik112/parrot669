## BUG-013

**Раздел:** Host / UI / Address  
**Серьёзность:** P2 — заметно мешает выбору адреса.  
**Название:** Автозаполнение браузера закрывает первый результат подсказок улиц.  
**Статус:** Подтверждено снимком пользователя; независимый повтор в браузере с сохранёнными адресами — **Нужна проверка**.

### Шаги воспроизведения

Предусловие: в браузере сохранён адрес; включены его подсказки адресов.

1. Открыть создание объекта либо изменение адреса существующего объекта.
2. Выбрать страну и город.
3. В поле «Улица» ввести `carrer de`.
4. Дождаться вариантов PARROT и браузерного автозаполнения.

### Фактическое поведение

Над списком PARROT появляется отдельное тёмное окно с сохранённой улицей и пунктом **«Manage addresses…»**. На снимке оно перекрывает часть первого результата, включая название/адрес. Одновременно конкурируют два списка выбора.

По внешнему виду и надписи это браузерное автозаполнение адресов. Это не окно ошибки LocationIQ и не отдельный диалог PARROT.

### Ожидаемое поведение

Пользователь видит первый и остальные варианты улиц, понимает, из какого списка выбирать, и может выбрать нужную улицу мышью или клавиатурой без перекрытия.

### Почему это важно

Первый подходящий результат выглядит закрытым непонятным окном. Можно выбрать сохранённый адрес браузера вместо нормализованной улицы PARROT и затем не понять, почему адрес не принимается.

### Возможное исправление

Устранить конкуренцию браузерного автозаполнения с собственным адресным combobox. **Не ограничиваться добавлением `autocomplete="off"`: атрибут уже присутствует.** Конкретный способ подавления/согласования подсказок подобрать и подтвердить в воспроизводящем браузерном профиле. Изменение `z-index` списка сайта само по себе не является доказанным решением для окна браузера.

Сохранить выбор из списка PARROT, клавиатурную навигацию и доступные подписи. Не требовать от пользователя отключать автозаполнение во всём браузере как постоянное решение.

### Критерии приёмки

- В браузере с сохранёнными адресами первый результат PARROT остаётся читаемым и выбираемым.
- Проверены создание объекта и изменение адреса; мышь, стрелки/Enter и Escape.
- Подстановка сохранённого адреса не создаёт ложного впечатления, что нормализованная улица уже выбрана.
- Отдельно проверены поддерживаемые мобильные браузеры; desktop-проверка не закрывает touch.

**Доказательство:** [снимок пользователя 09:05:49](evidence/01-street-autofill.png).  
**Код:** [host-address.js](https://github.com/lelik112/parrot669/blob/be7fc39c260627822c00292523c502c7b93bb879/public/assets/host-address.js), функция `lookup`, строки 64–83: собственный combobox/listbox и `input.autocomplete="off"`.

## BUG-014

**Раздел:** Host / UI  
**Серьёзность:** P2 — неверно воспринимается назначение целого раздела.  
**Название:** Раздел закрытых дат выглядит как сообщение об отсутствии доступа к функции.  
**Статус:** Подтверждено пользовательским снимком, текущим текстом и CSS.

### Шаги воспроизведения

1. Открыть кабинет на русском языке.
2. Развернуть объект.
3. Перейти к форме добавления недоступных дат, особенно когда сохранённых блокировок ещё нет.

### Фактическое поведение

Заголовок **«НЕДОСТУПНО · РУЧНЫЕ БЛОКИРОВКИ»** написан розово-красным; рамка, подписи и кнопка поддерживают оформление предупреждения. Без чтения пояснения «Недоступно» воспринимается как состояние функции или прав пользователя.

Дополнительно пояснение **«Обе даты заблокированы…»** показано над ещё пустыми полями. Фактической блокировки пока нет, однако текст сформулирован как сообщение о выполненном действии.

### Ожидаемое поведение

С первого взгляда понятно: здесь владелец закрывает выбранные ночи для поиска. Раздел доступен, а блокировка появится только после сохранения.

### Почему это важно

Владелец может решить, что функция отключена, требует проверки или дополнительных прав. Штатная настройка выглядит как ошибка, а текст над пустой формой сообщает результат до действия.

### Возможное исправление

| Элемент | Предлагаемый текст/оформление |
| --- | --- |
| Заголовок | **Закрытые даты** |
| Пояснение | «Укажите ночи, когда жильё недоступно гостям. Они не попадут в поиск; свободные периоды и цены сохранятся.» |
| Начало | «Первая закрытая ночь» |
| Конец | «Последняя закрытая ночь» |
| Подсказка к диапазону | «Обе выбранные ночи включены в период.» |
| Основная кнопка | **Закрыть даты** |
| Пустое состояние | «Закрытых дат пока нет.» |
| Успешное сохранение | «Даты закрыты для поиска.» |

Использовать обычный цвет заголовка и нейтральную рамку формы. Цвет закрытых дат можно оставить в отметках уже сохранённых периодов; оформление ошибки применять к ошибке или действительно недоступному действию. Верхний регистр для этого заголовка убрать.

### Критерии приёмки

- Пустая форма не утверждает, что даты уже закрыты.
- Заголовок описывает даты, а не доступ пользователя к разделу.
- Понятно, что последняя выбранная ночь включается.
- Сохранение и снятие блокировки продолжают работать как раньше; изменение текста не меняет диапазоны или цены.

**Доказательство:** [снимок пользователя 09:07:57](evidence/02-manual-blocks-copy.png).  
**Код:** [host.js](https://github.com/lelik112/parrot669/blob/be7fc39c260627822c00292523c502c7b93bb879/public/assets/host.js), `blockCopy.ru` и переопределение `hostDateCopy.ru`, строки 94–108; [styles.css](https://github.com/lelik112/parrot669/blob/be7fc39c260627822c00292523c502c7b93bb879/public/assets/styles.css), стили `.host-unavailability-panel`, строки 1477–1481.

## PRODUCT-001

**Раздел:** Host / Search / Backend contract  
**Серьёзность:** P1 — предлагаемый приоритет нового правила публикации ссылки.  
**Название:** Внешняя ссылка публикуется до подтверждения управления календарём.  
**Статус:** Текущее поведение подтверждено; **это изменение продуктового правила**, а не нарушение действующей документации.

### Шаги воспроизведения

1. Добавить к объекту внешнее объявление Airbnb.
2. Подключить соответствующий календарь, не проходя проверку.
3. Посмотреть галку «Показывать внешнюю ссылку в поиске» и состояние проверки.

Для окончательной проверки гостевого результата: найти объект по его свободным датам и проверить наличие ссылки в карточке.

### Фактическое поведение

На снимке одновременно видны включённая галка и статус **«Требуется проверка»**.

Код подтверждает, что это не только визуальная галка:

- создание listing задаёт `showInSearch = true`;
- переключатель не блокируется по статусу проверки;
- обновление видимости проверяет владельца listing, но не результат calendar verification;
- выдача включает ссылки по `showInSearch`, без проверки calendar verification.

Фактический гостевой переход для этого конкретного объекта в текущем авторизованном прогоне не проверялся.

### Действующий контракт и желаемое поведение

В [product-context.md](https://github.com/lelik112/parrot669/blob/be7fc39c260627822c00292523c502c7b93bb879/docs/product-context.md) видимость внешней ссылки описана как независимая настройка. [Документ проверки календаря](https://github.com/lelik112/parrot669-backend/blob/b5ac2a2a266fa81bb840086928b6234d9d575f33/docs/calendar-ownership-verification.md) отдельно говорит, что проверка не меняет поиск.

Новое пожелание владельца продукта: **разрешать публикацию внешней ссылки после успешной проверки календаря**. Предлагаемая последовательность:

| Состояние | Галка | Пояснение |
| --- | --- | --- |
| Объявление добавлено, календаря нет | Выключена и disabled | «Подключите календарь Airbnb и пройдите проверку, чтобы показывать ссылку гостям.» |
| Проверка required / pending / failed / blocked | Выключена и disabled | «Ссылка появится в поиске после проверки календаря и вашего разрешения.» |
| verified для текущего источника | Доступна, изначально выключена | «Показывать ссылку Airbnb в поиске» |
| Источник заменён/удалён, подтверждение потеряно | Публичный показ прекращён | Понятно объяснить необходимость новой проверки. |

Выключенное состояние после успешной проверки — рекомендация: публикация выполняется явным действием владельца. Это дополнительное решение интерфейса, не уже реализованное требование.

### Почему это важно

Сейчас визуально проверка и публикация относятся к одному объявлению, но первая никак не ограничивает вторую. По новому продуктовому ожиданию гости должны получать внешнюю ссылку только после подтверждения текущего источника.

Это подтверждение управления календарём; текст интерфейса не должен превращать его в обещание проверки личности или права собственности.

### Возможное исправление

Согласованно изменить правило в форме, серверном обновлении видимости и публичной выдаче. Одного `disabled` на галке недостаточно: сервер должен применять то же правило к запросам и старым сохранённым значениям.

Сохранить возможность находить сам объект по доступности без внешней ссылки. Связь проверки с публикацией ссылки не должна делать внешнее объявление обязательным для участия объекта в поиске.

### Критерии приёмки

- Новое объявление не публикует ссылку автоматически.
- До verified для текущего источника галку нельзя включить, а сервер не принимает запрос на публикацию.
- У старых listing с `showInSearch=true` отсутствие подтверждения не приводит к показу ссылки.
- После проверки владелец может явно включить/выключить показ.
- Замена/удаление источника не оставляет публичную ссылку с утраченным подтверждением.
- Объект без опубликованной ссылки остаётся доступен в поиске при подходящих датах.
- Учитывается существующее правило: обычное выключение/включение синхронизации сохраняет verified; его не следует случайно приравнять к замене источника.

**Код:** [host.js](https://github.com/lelik112/parrot669/blob/be7fc39c260627822c00292523c502c7b93bb879/public/assets/host.js), `updateListingVisibility` и создание `visibilityCheckbox`; [PropertyService.scala](https://github.com/lelik112/parrot669-backend/blob/b5ac2a2a266fa81bb840086928b6234d9d575f33/src/main/scala/com/parrot669/housing/PropertyService.scala), `addListing` / `updateListing`; [SearchService.scala](https://github.com/lelik112/parrot669-backend/blob/b5ac2a2a266fa81bb840086928b6234d9d575f33/src/main/scala/com/parrot669/search/SearchService.scala), `links = listings.filter(_.showInSearch)`.

## BUG-015

**Раздел:** Host / Calendar / UI  
**Серьёзность:** P1 — мешает пройти проверку и может привести к исчерпанию попыток.  
**Название:** Проверка календаря теряет инструкцию и не удерживает пользователя на шаге изменения дат в Airbnb.  
**Статус:** Начальное и ожидающее состояния подтверждены снимками пользователя; промежуточное состояние и переход проверены по текущему UI-коду. Полный независимый цикл с реальным изменением Airbnb — **Нужна проверка**.

### Шаги воспроизведения

1. Открыть подключённый календарь со статусом «Требуется проверка».
2. Нажать «Начать проверку» и дождаться получения исходного состояния.
3. Не меняя календарь Airbnb, нажать появившуюся кнопку «Проверить».
4. Посмотреть, какое действие и инструкция доступны после перехода в ожидание.

На двух предоставленных снимках видны состояние перед началом и итоговое ожидание. Точное нажатие пользователя между снимками не зафиксировано; последовательность выше соответствует обработчикам текущего интерфейса.

### Фактическое поведение

- В начале есть одно общее предложение «выберите подходящий период в Airbnb, измените его доступность…».
- После получения исходного состояния заголовок **«Можно проверять»** и короткая кнопка **«Проверить»** не подчёркивают, что сначала нужно совершить отдельное действие в Airbnb.
- Инструкция не объясняет, что подходят сегодняшние/будущие ночи, а изменение только прошлых дат не учитывается.
- После «Проверить» инструкция заменяется текстом **«Проверим сразу, затем автоматически через 5, 10 и 20 минут. Страницу можно закрыть.»** Появляются время следующей проверки и «Попытка 1 из 3».
- В этом состоянии нет ни первоначальной инструкции, ни отдельного действия «Что нужно изменить?». Пользователь остаётся с ожиданием и не понимает, чего система ждёт.

Фраза «Проверим сразу» остаётся в уже ожидающем состоянии и дополнительно затрудняет понимание, была ли немедленная проверка выполнена.

### Ожидаемое поведение

Пользователь на каждом этапе понимает:

1. исходное состояние уже получено или ещё загружается;
2. даты выбираются и изменяются **в календаре этого объявления на Airbnb**;
3. подходит изменение будущего свободного периода; прошлые даты не помогут;
4. в PARROT нужно вернуться после сохранения изменения;
5. во время ожидания инструкция остаётся доступной.

**Само отсутствие выбора дат внутри PARROT не является багом текущего контракта.** Сервис не назначает конкретный диапазон и не принимает выбранные даты: он ищет изменение доступности в iCal после начального снимка. Проблема — в объяснении и переходах пользовательского сценария.

### Почему это важно

Пользователь может нажать «Проверить» без изменения календаря и ждать результата, который не появится. Одна попытка уже началась; отсутствие изменений или истечение времени могут завершить её неудачей. По документации после трёх неудачных попыток проверка блокируется на 24 часа. Эта блокировка не воспроизводилась на production.

### Возможное исправление

| Этап | Предлагаемое содержание |
| --- | --- |
| До начала | «Проверим, что вы можете изменить календарь этого объявления на Airbnb.» Кнопка «Начать проверку». |
| Получение исходного состояния | «Получаем календарь Airbnb. Пока не меняйте даты.» |
| Нужен шаг владельца | Заголовок **«Измените даты в Airbnb»**. Короткие нумерованные действия: открыть календарь этого объявления; выбрать свободные будущие ночи и временно закрыть их либо открыть безопасный ранее закрытый период; сохранить изменение; вернуться сюда. |
| Переход к проверке | Кнопка **«Я изменил даты — проверить»**. Рядом срок завершения текущей попытки. |
| Изменение ещё не обнаружено | «Изменение пока не видно в календаре Airbnb. Следующая проверка: …». Инструкцию оставить видимой либо доступной через «Как изменить даты в Airbnb?». |
| Успех | «Управление календарём подтверждено». Объяснить, что временное изменение теперь можно вернуть. |

Указать, что не нужно изменять существующие брони. Перед началом объяснить лимит попыток. Дать понятный путь к Airbnb; обычную ссылку на публичное объявление не выдавать за прямой переход в календарь владельца.

Не добавлять обязательный выбор диапазона в PARROT только ради исправления текста: это изменило бы текущий контракт проверки. Для описанной проблемы достаточно ясных шагов, названия действия и постоянной инструкции.

### Критерии приёмки

- После Start главный следующий шаг — изменение календаря в Airbnb.
- Явно сказано, где выбираются даты и что прошлые даты не учитываются.
- Проверку пользователь запускает действием, название которого подтверждает совершённое изменение.
- После преждевременного Check и после перезагрузки инструкция остаётся доступна.
- В ожидании показаны следующий запуск и состояние текущей попытки, без ложного обещания уже выполненного действия.
- После успеха объяснено, когда можно вернуть тестовое изменение.
- Полный цикл проверен владельцем на контролируемом календаре; его реальные брони не меняются.

## Передача разработчику

Начать с BUG-015 и PRODUCT-001: они определяют прохождение проверки и смысл публикации ссылки. Затем BUG-013 и BUG-014.

После исправлений выполнить отдельный авторизованный ретест: создание/редактирование адреса с браузерным autofill; пустая и заполненная форма закрытых дат; публикация ссылки во всех состояниях проверки, включая старые записи; Start → изменение Airbnb → Check → ожидание → успех/ошибка. Мобильные проверки провести отдельно.

Скриншоты в `evidence/` предоставлены пользователем, сохранены без изменения пикселей. Их время — из имён исходных файлов; часовой пояс по снимкам не устанавливался. Прошлые закрытые баги и GEO-ретест этим отчётом не переоткрываются.
